기존 코드베이스 파악하기

내가 짜지 않은 시스템을 넘겨받았을 때, 코드를 건드리지 않고 구조와 진입점을 파악합니다. Claude의 답을 그대로 믿지 않고 확인된 사실과 추측을 갈라내는 방법이 이 모듈의 핵심입니다.

2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. Plan 모드로 코드를 수정하지 않고 코드베이스의 구조와 실제 진입점을 파악할 수 있다.
  2. 신뢰도 라벨을 요구해 확인된 사실과 추측을 갈라낸 인수인계 문서를 만들 수 있다.
  3. 확인된 위험 지점만 골라 CLAUDE.md에 남겨 다음 세션과 팀에 넘길 수 있다.

3. 사전 준비

설명

3-1. 준비물

항목내용
필요 플랜Pro 이상.
설치초급 01에서 완료. 추가 설치 없음.
사전 지식Claude Code 초급 5개 모듈 전부 수료. 특히 초급 02의 Plan 모드와 초급 04의 CLAUDE.md를 씁니다.
실습 대상초급에서 써 온 같은 샌드박스. 이 모듈 1단계에서 "인수인계 상태"로 확장합니다.
예상 사용량프롬프트 5회(A~E). 정찰은 파일을 여러 개 읽으므로 초급보다 많이 씁니다.

3-2. 이 문서의 표기 방식

초급과 같습니다. 커맨드·파일명·화면 문구는 영문 원문 그대로 싣고 설명만 한국어로 씁니다.

3-3. 샌드박스를 확장합니다

왜 확장하는가

초급 5개 모듈을 마친 샌드박스는 파일이 7개뿐이라 (CLI 실행 결과 직접 확인, 2026-08-26) "정찰"할 것이 없습니다. 1단계에서 스크립트를 한 번 실행해 문서가 낡고, 진입점이 여러 개이고, 쓰이는지 알 수 없는 코드가 섞인 상태로 확장합니다. 실제 인수인계 상황과 같은 조건을 만들기 위해서입니다.

확장은 파일 추가만 합니다. 초급에서 만든 app.py·CLAUDE.md·커밋 이력은 그대로 남습니다.

4. 핵심 개념

설명

4-1. 결론부터

모르는 코드베이스에서 가장 위험한 것은 Claude가 틀리는 것이 아니라, 맞는 말과 추측을 같은 어조로 말하는 것입니다. 코드에서 확인한 것과 그럴듯하게 추론한 것을 Claude는 똑같이 자신 있게 씁니다. 그 둘을 갈라내지 않으면 추측이 문서에 박히고, 문서가 다음 사람의 사실이 됩니다.

4-2. 신뢰도 라벨

해결책은 주장마다 근거의 강도를 표시하게 하는 것입니다. 이 커리큘럼은 4단계를 씁니다.

라벨의미이 샌드박스에서의 예
[FACT]코드나 문서에서 직접 확인됨app.py가 inventory.csv를 읽는다 — 코드에 그대로 있음
[STRONG]강한 근거가 있는 추론scripts/daily_batch.sh가 운영 진입점이다 — 주석에 실행 시각이 적혀 있음
[WEAK]약한 추론, 확인 필요utils/legacy_export.py가 아직 쓰인다 — 배치가 호출하지만 배치가 실제로 도는지는 알 수 없음
[GUESS]순전한 추측retry = 3의 이유 — 근거가 코드에도 주석에도 없음
라벨의 진짜 쓸모는 [WEAK]와 [GUESS]입니다

[FACT]는 어차피 코드를 보면 압니다. 라벨이 값어치를 하는 지점은 "이건 내가 사람에게 물어봐야 하는구나"를 골라 주는 것입니다. [WEAK]와 [GUESS] 항목이 곧 인수인계 미팅에서 던질 질문 목록이 됩니다.

4-3. 문서를 믿지 말고 진입점을 찾습니다

넘겨받은 프로젝트의 README는 대개 낡아 있습니다. 마지막으로 갱신된 시점 이후에 운영 방식이 바뀌었기 때문입니다. README가 안내하는 실행 방법과 실제 운영에서 도는 것이 다른지를 초반에 확인해야 합니다.

확인 방법은 단순합니다. 실행 가능한 것을 전부 찾은 뒤(스크립트, 배치 파일, 진입점 함수), 각각이 문서에 언급돼 있는지 대조합니다. 문서에 없는 실행 경로가 진짜 운영 경로인 경우가 많습니다.

4-4. 읽기만 하는 정찰은 Plan 모드로

초급 02에서 배운 Plan 모드를 그대로 씁니다. 이 모드에서 Claude는 파일을 읽고 탐색 명령을 실행해 계획을 세우지만 소스를 편집하지 않습니다. (출처: code.claude.com/docs/en/permission-modes, 2026-08-26 확인) 모르는 코드베이스에서 첫 세션에 파일이 바뀌는 것은 그 자체로 사고입니다.

4-5. 정찰 결과는 반드시 파일로 남깁니다

세션이 끝나면 대화는 사라집니다. 정찰에 30분을 썼는데 결과가 세션 안에만 있으면 다음 세션에 처음부터 다시 해야 합니다. 이 모듈은 두 곳에 남깁니다.

어디에무엇을왜
docs/HANDOVER.md정찰 결과 전문 (라벨 포함)길어도 됨. 필요할 때 찾아 읽는 문서
CLAUDE.md확인된 위험 지점 몇 줄만매 세션 로드되므로 짧아야 함. 공식 문서는 파일당 200줄 미만을 목표로 하며, 길수록 컨텍스트를 많이 쓰고 준수도가 떨어진다고 안내합니다 (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)
CLAUDE.md에 [GUESS]를 옮기지 마세요

CLAUDE.md는 매 세션 시작 시 Claude가 읽는 파일입니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인) 추측을 여기 적으면 다음 세션부터 그 추측이 전제로 작동합니다. 옮기는 것은 [FACT]와, 사람에게 확인을 받은 [STRONG] 항목뿐입니다.

5. 단계별 실습

실습

만들 결과물: 신뢰도 라벨이 붙은 docs/HANDOVER.md 1건. 마지막에 그중 확인된 항목만 CLAUDE.md로 옮깁니다.

  3. Plan 모드로 세션을 시작합니다

    claude로 세션을 열고 Shift+Tab으로 상태 표시줄이 ⏸ plan mode on이 되게 합니다. 정찰이 끝날 때까지 이 모드를 유지합니다.

  4. 구조와 진입점을 정찰합니다 (프롬프트 A)

    아래를 보냅니다. 구조와 진입점을 한 번에 묻는 것이 요령입니다. 진입점을 따로 묻지 않으면 Claude가 README를 그대로 옮겨 적는 경우가 많습니다.

    프롬프트
    이 저장소를 처음 인수인계받았습니다. 코드를 수정하지 말고 파악만 해 주세요.

1. 디렉터리 구조와 각 파일의 역할
2. 실행 가능한 진입점을 모두 찾아 주세요 (스크립트, 배치, main 함수 등)
3. 각 진입점이 README나 CLAUDE.md에 언급돼 있는지 대조해 주세요
  5. README와 실제의 차이를 직접 확인합니다

    Claude의 답을 그대로 믿지 말고 터미널에서 직접 대조합니다.

    셸 명령 · 예상 출력
    $ grep -c 'daily_batch' README.md CLAUDE.md

$ head -2 scripts/daily_batch.sh | tail -1
# 2024-11 이관. 운영 크론에서 매일 07:00 실행.

    문서 어디에도 없는 스크립트가 운영에서 매일 돌고 있습니다. 이것이 4-3에서 말한 상황입니다.

    여기까지 — 정찰
    • 파일을 하나도 수정하지 않았다 (⏸ plan mode on 유지)
    • 진입점이 2개 이상이라는 것을 확인했다
    • 그중 문서에 없는 것이 있다는 것을 직접 grep으로 확인했다

    Claude가 진입점을 하나만 찾았다면 프롬프트 A의 2번 항목을 다시 강조해 물어보세요. 문서만 보고 답한 것입니다.

  6. 신뢰도 라벨을 붙인 문서를 요청합니다 (프롬프트 B)

    이제 정찰 결과를 문서로 만듭니다. 라벨을 요구하는 것이 이 단계의 전부입니다.

    프롬프트
    지금까지 파악한 내용을 인수인계 문서 초안으로 정리해 주세요.
아직 파일로 저장하지는 마세요.

모든 항목 앞에 근거 강도를 라벨로 붙여 주세요.
- [FACT] 코드나 설정 파일에서 직접 확인한 것

  7. [FACT] 항목 하나를 직접 검증합니다

    라벨을 요구했다고 라벨이 정확한 것은 아닙니다. [FACT]로 표시된 항목 중 하나를 골라 터미널에서 직접 확인하세요.

    셸 명령 예시

    [FACT]인데 코드에서 확인되지 않는 항목이 있다면, 그 문서의 라벨 전체를 다시 의심해야 합니다.

  8. 확인 질문 목록을 뽑습니다 (프롬프트 C)

    [WEAK]와 [GUESS] 항목을 사람에게 물어볼 질문으로 바꿉니다. 이것이 인수인계 미팅의 안건이 됩니다.

    프롬프트
    [WEAK]와 [GUESS]로 표시한 항목만 모아,
전임 담당자에게 물어볼 질문 목록으로 바꿔 주세요.

각 질문에 왜 코드만으로는 알 수 없는지 한 줄로 덧붙여 주세요.
    여기까지 — 문서 초안
    • 모든 항목에 4개 라벨 중 하나가 붙어 있다
    • [FACT] 항목 하나를 직접 검증했다
    • [WEAK]·[GUESS]가 질문 목록으로 바뀌었다

    라벨이 전부 [FACT]거나 전부 [STRONG]이면 라벨링이 형식적으로만 이뤄진 것입니다. 이 샌드박스에는 코드만으로 알 수 없는 항목이 분명히 있으니, 프롬프트 B를 다시 보내며 "확실하지 않은 것은 반드시 [WEAK]나 [GUESS]로 표시하라"고 강조하세요.

import sys
import os

from utils.notify import send

OUT_DIR = "/tmp/inventory_out"


def export(path):
    if not os.path.exists(OUT_DIR):
        os.makedirs(OUT_DIR)
    with open(path, encoding="utf-8") as f:
        lines = [l.rstrip("\n") for l in f if l.strip()]
    dest = os.path.join(OUT_DIR, "latest.txt")
    with open(dest, "w", encoding="utf-8") as f:
        f.write("\n".join(lines))
    try:
        send(len(lines))
    except Exception:
        pass
    return dest


if __name__ == "__main__":
    if len(sys.argv) > 1:
        print(export(sys.argv[1]))
EOF

cat > utils/notify.py << 'EOF'
import configparser
import os

WEBHOOK_URL = "https://ops-internal.example.corp/hooks/inventory"
DRY_RUN = True

_cfg = configparser.ConfigParser()
_cfg.read(os.path.join(os.path.dirname(__file__), "..", "config", "settings.ini"))


def send(count):
    retry = _cfg.getint("notify", "retry", fallback=3)
    if DRY_RUN:
        print(f"[DRY_RUN] would POST count={count} to {WEBHOOK_URL} (retry={retry})")
        return True
    raise NotImplementedError("운영 전환 시 구현 필요")
EOF

[notify]
retry = 3

Plan 모드의 동작(읽기와 탐색은 하되 소스를 편집하지 않음), Shift+Tab으로 뜨는 상태 표시줄 문구(⏸ plan mode on, ⏸ manual mode on)는 권한 모드 공식 문서로 재확인했습니다. CLAUDE.md의 200줄 미만 권장 기준과 매 세션 로드 방식은 메모리 공식 문서로 재확인했습니다. 신뢰도 라벨 4단계는 Anthropic 공식 기능이 아니라 이 커리큘럼이 정한 프롬프트 규약입니다 — 제품에 그런 기능이 있는 것이 아니라, 프롬프트로 요구하는 것입니다.

실습 흐름은 이번 확인에서 claude -p --permission-mode plan(프롬프트 A·B·C)과 --permission-mode manual·acceptEdits(프롬프트 D·E)로 같은 세션을 이어가며 처음부터 끝까지 직접 재현했습니다. Plan 모드에서는 5단계 내내 파일이 하나도 바뀌지 않았고(git status 계속 클린), Manual 모드에서는 docs/HANDOVER.md 쓰기가 승인 없이는 permission_denials로 막히는 것도 확인했습니다. 그 과정에서 다음을 바로잡았습니다 — (1) git init 직후 브랜치 이름은 init.defaultBranch를 설정하지 않은 환경에서 main이 아니라 master로 생성됨(초급 03·04에서도 확인된 동일 사안)을 재확인해 11단계 예시에 안내를 추가, (2) 확장 스크립트가 "파일 5개 추가"라고 한 것을 git show --stat로 대조해 실제로는 새 파일 4개 + 내용이 같아 변경으로 안 잡히는 .gitignore 재작성임을 확인해 수정, (3) "예상 사용량: 프롬프트 4회"를 실제 프롬프트 A~E 5회에 맞게 수정, (4) "초급 샌드박스는 파일 5개뿐"이라는 서술을 초급 5개 모듈을 마친 실제 상태(7개)에 맞게 수정, (5) "7. 트러블슈팅" 절의 ModuleNotFoundError 항목을 재현 테스트해 원인을 바로잡음 — scripts/daily_batch.sh는 실행 위치와 무관하게 항상 성공했고, 에러는 python3 -m utils.legacy_export를 저장소 루트 밖에서 직접 실행할 때만 재현됨. find·grep 예상 출력과 count=2 DRY_RUN 로그, 프롬프트 A~E의 응답 형태(라벨 4종 모두 등장, 진입점 3개 탐지, CLAUDE.md에 WEAK/GUESS 미유입)는 재구성한 샌드박스에서 그대로 재현되어 원문 그대로 두었습니다.

C-01 목업 완성(2026-08-27): 대화형 claude는 이 클라우드 환경에서 OAuth 로그인 화면으로 막혀 승인 화면 자체를 캡처할 수 없음을 재확인했습니다. 대신 위와 같은 방식으로 샌드박스를 다시 재현하고 프롬프트 A~D를 실제 실행해 얻은 docs/HANDOVER.md(91줄, [FACT] 24 · [STRONG] 3 · [WEAK] 9 · [GUESS] 1)의 실제 앞부분을 승인 화면 목업에 반영했습니다.
