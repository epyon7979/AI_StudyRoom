4. 핵심 개념

설명

4-1. 결론부터

매번 같은 것을 승인하고 있다면 그건 승인이 아니라 습관입니다. 습관이 되면 화면을 안 읽게 되고, 안 읽으면 권한 모드가 무의미해집니다. 안전한 것은 규칙으로 통과시키고, 위험한 것만 화면에 남기는 것이 이 모듈의 목적입니다.

4-2. 설정 파일은 4종입니다

Claude Code는 네 개의 설정 파일에서 설정을 읽고, 조직은 claude.ai 콘솔에서 관리 설정을 전달할 수도 있습니다. 어느 파일에 넣느냐가 곧 누구에게 적용되느냐입니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

범위파일적용 대상주로 넣는 것
사용자~/.claude/settings.json나, 이 기기의 모든 프로젝트개인 취향(테마·기본 모델)과 내 권한 규칙
공유 프로젝트.claude/settings.json이 폴더에서 시작하는 모두. git에 커밋하면 팀 전체팀 권한·훅·플러그인, 프로젝트에 필요한 환경 변수
프로젝트 로컬.claude/settings.local.json나, 이 프로젝트에서만한 프로젝트의 개인 오버라이드, 공유 전 테스트
관리managed-settings.json 등조직이 배포한 모두보안 정책과 컴플라이언스
설치해도 설정 파일은 생기지 않습니다

Claude Code를 설치한다고 설정 파일이 만들어지지는 않습니다. 이미 있다면 조직이 배포했거나, 프로젝트에 커밋돼 있었거나, 내가 만들었거나, Claude Code가 알아서 만든 것입니다. 후자의 대표적인 경우가 /config에서 테마를 바꿀 때(사용자 파일)와, 권한 프롬프트에서 "Yes, and don't ask again"을 고를 때(프로젝트 로컬 파일)입니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

초급 03에서 "Yes, and don't ask again"을 고르지 말라고 했던 이유가 이것입니다. 그 선택은 설정 파일에 규칙을 쌓는 행위였습니다.

4-3. 같은 키가 여러 곳에 있으면

높은 단계의 값이 아래 단계의 같은 키를 덮어씁니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

순위출처정하는 사람
1 (최상위)관리 설정조직 — 내가 무엇을 넣어도 못 바꿈
2명령줄 (claude --settings)나, 이 세션만
3.claude/settings.local.json나, 이 프로젝트
4.claude/settings.json프로젝트의 모두
5 (최하위)~/.claude/settings.json나, 모든 프로젝트
목록 키는 덮어쓰지 않고 합쳐집니다

permissions.allow 같은 목록 키를 여러 파일에 설정하면, Claude Code는 하나를 고르는 대신 목록을 합칩니다. 각 파일이 다른 파일의 항목을 지우지 않고 자기 항목을 더할 수 있습니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

즉 팀 파일의 allow 규칙을 내 파일로 "빼는" 것은 안 됩니다. 빼려면 팀 파일을 고쳐야 합니다.

4-4. allow와 deny를 고르는 기준

규칙넣어도 되는 것넣으면 안 되는 것
allow 결과를 되돌릴 수 있고, 대상이 명확히 좁은 것. 읽기 계열(git status, git log), 프로젝트의 테스트·린트 명령 Bash(*)처럼 넓은 규칙, 네트워크로 나가는 명령, 파일을 지우거나 되돌리는 명령
deny 자격 증명·비밀이 담긴 파일(.env 계열), 읽힐 필요가 없는 개인 파일 —
allow는 권한 모드를 무력화할 수 있습니다

초급 02에서 배운 권한 모드는 "무엇을 물어볼지"를 정하고, allow 규칙은 "무엇을 안 물어볼지"를 정합니다. allow를 넓게 잡으면 Manual 모드로 두어도 실질적으로 Auto가 됩니다. 규칙 하나를 추가할 때마다 "이게 잘못 실행되면 되돌릴 수 있나"를 먼저 물으세요.

git status·git log·git diff는 사실 이미 승인 없이 실행됩니다

Claude Code는 ls·cat·pwd·grep·find 같은 읽기 전용 명령과 git의 읽기 전용 하위 명령(status·log·diff 등)을 모든 권한 모드에서 이미 내장으로 승인 없이 실행합니다. 이 내장 목록은 설정으로 끄거나 바꿀 수 없습니다. (출처: code.claude.com/docs/en/permissions, 2026-08-26 확인)

즉 6번 절 예제의 Bash(git status)·Bash(git log *)·Bash(git diff *) 규칙은 없어도 이 세 명령은 원래 안 물어봅니다. 그래도 이 규칙들을 넣는 이유는, 정책을 settings.json에 명시적으로 남겨 두면 /permissions에서 출처를 확인하거나 allowManagedPermissionRulesOnly 같은 조직 정책과 조합할 때 의도가 분명해지기 때문입니다. 다만 이 세 명령으로는 방금 만든 allow 규칙이 실제로 뭔가를 바꿨는지 확인할 수 없습니다 — 규칙이 없어도 결과가 똑같기 때문입니다. 그래서 5단계 실습의 프롬프트 A는 내장 목록에 없는 명령으로 규칙의 효과를 직접 확인합니다.

4-5. 설정 파일은 엄격한 JSON입니다

설정 파일은 엄격한 JSON이라 // 주석이나 뒤따르는 쉼표는 문법 오류이고, 다음 시작 시 Settings Error로 보고됩니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

표시무슨 뜻인가어떻게 되는가
Settings Error파일 전체가 잘못된 JSON이거나 스키마가 거부하는 값세션 시작 시 대화상자가 뜨고, 고치거나 종료하거나 그 설정 없이 계속할 수 있음
Settings Warning개별 항목만 잘못됨 (예: 형식이 틀린 권한 규칙)그 값만 건너뛰고 파일의 나머지는 적용됨

파일 첫 줄의 $schema는 공식 JSON 스키마를 가리키며, VS Code·Cursor 등 JSON 스키마를 지원하는 에디터에서 자동완성과 인라인 검증을 제공합니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

4-6. 확인하는 두 가지 명령

명령구분무엇을 보여주는가
/status세션Setting sources 줄에 이번 세션이 읽은 설정 파일이 나열됨. 어느 파일이 어느 키를 줬는지는 안 나옴
claude doctor셸Claude Code가 거부한 항목의 상세 내용

대부분의 편집은 재시작 없이 실행 중인 세션에 반영됩니다(permissions 포함). 다만 model·effortLevel·outputStyle은 세션 시작 시 한 번만 읽으므로 각각 /model·/effort·/clear가 필요합니다. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

5. 단계별 실습

실습

만들 결과물: 동작이 확인된 개인 설정 파일 ~/.claude/settings.json 1개.

  1. 지금 설정 파일이 있는지 확인합니다
    셸 명령
    ls -la ~/.claude/ 2>/dev/null | grep settings
ls -la .claude/ 2>/dev/null

    아무것도 안 나오면 정상입니다(4-2). ~/.claude/settings.json이 이미 있다면 3-3의 백업 명령을 먼저 실행한 뒤 진행하세요.

  2. 세션을 열고 현재 설정 소스를 봅니다

    샌드박스에서 claude로 세션을 열고 아래를 입력합니다. Status 탭의 Setting sources 줄을 확인하세요. 이것이 4단계 이후와 비교할 대조군입니다.

    세션 커맨드
    /status
  3. deny 규칙을 시험할 파일을 만듭니다

    터미널에서 실행합니다. 실제 비밀이 아니라 실습용 더미 값입니다.

    셸 명령
    cd ~/claude-code-sandbox
printf 'API_KEY=dummy-not-a-real-secret\n' > .env
printf '.env\n' >> .gitignore

    .gitignore에 함께 넣는 이유는, 실제 .env는 절대 커밋하면 안 되기 때문입니다. deny 규칙은 커밋 차단과 별개로 Claude가 읽는 것을 막습니다.

  4. 개인 설정 파일을 만듭니다

    6번 절의 설정 파일 전문을 그대로 ~/.claude/settings.json에 저장합니다. 에디터로 만들어도 되고 아래처럼 만들어도 됩니다.

    셸 명령 (디렉터리가 없을 경우 대비)
    mkdir -p ~/.claude

    저장 후 JSON이 유효한지 먼저 확인하세요. 오류가 있으면 아무것도 적용되지 않습니다.

    셸 명령 · 예상 출력
    $ python3 -m json.tool ~/.claude/settings.json > /dev/null && echo "JSON OK"
JSON OK
  5. /status로 로드됐는지 확인합니다

    세션으로 돌아와 다시 입력합니다. Setting sources 줄에 User settings가 나타나야 합니다. 2단계와 비교하세요.

    세션 커맨드
    /status
    [캡처 C-01]
    화면
    /status의 Setting sources 줄
    진입 경로
    설정 파일 저장 후 세션에서 /status 실행
    캡처 범위
    Status 탭에서 Setting sources 줄이 보이는 범위
    강조 표시
    Setting sources 줄(빨간 테두리)
    캡션
    설정 파일이 실제로 로드됐는지는 /status의 Setting sources로 확인한다.
    근사 목업 실제 화면과 다를 수 있는 근사 목업입니다. /status는 대화형 세션에서만 열리는 다이얼로그라, 이 클라우드 환경에서 claude -p "/status"를 실행하면 /status isn't available in this environment.라는 실제 응답만 돌아옵니다(2026-08-27 확인) — 1단계에서 본 대로 대화형 로그인 자체가 막혀 있기 때문입니다. 화면 구성은 공식 문서가 설명하는 Status 탭의 Setting sources 항목(로드된 각 설정 파일을 나열하는 줄) 구조를 따라 재구성했습니다 (출처: code.claude.com/docs/en/settings, 2026-08-27 확인). 다만 설정 파일이 실제로 로드되어 동작을 바꾼다는 사실 자체는 대화형 화면 없이 직접 확인했습니다 — 공식 문서의 "깨끗한 설정으로 테스트하기" 방법대로 CLAUDE_CONFIG_DIR을 빈 디렉터리로 지정하면 allow 규칙 없이 python3 -m json.tool ~/.claude/settings.json이 승인을 요구하며 막히고, 6번 절의 개인 설정 파일을 넣은 CLAUDE_CONFIG_DIR에서는 같은 명령이 승인 없이 즉시 실행되는 것을 claude -p로 직접 대조했습니다(2026-08-27) (출처: code.claude.com/docs/en/debug-your-config의 clean-configuration 절차, 2026-08-27 확인). 즉 아래 화면의 틀은 근사지만, 설정이 실제로 로드·적용된다는 내용은 실행으로 확인된 사실입니다.

    > /status

  6. allow 규칙이 동작하는지 확인합니다 (프롬프트 A)

    상태 표시줄이 ⏸ manual mode on인지 먼저 확인한 뒤 아래를 보냅니다. python3 -m json.tool은 4-4의 내장 읽기 전용 목록에 없어 원래는 매번 승인이 필요한 명령입니다. Manual 모드인데도 승인을 묻지 않고 바로 실행되면 방금 만든 allow 규칙이 동작한 것입니다.

    프롬프트
    python3 -m json.tool 명령으로 ~/.claude/settings.json이 유효한 JSON인지 확인해 주세요. 정확히 python3 -m json.tool ~/.claude/settings.json 명령을 실행하면 됩니다.
  7. deny 규칙이 동작하는지 확인합니다 (프롬프트 B)
    프롬프트
    .env 파일 내용을 보여 주세요.

    Claude가 읽지 못한다고 답해야 정상입니다. 내용이 그대로 나왔다면 deny 규칙이 적용되지 않은 것이니 7번 절을 확인하세요.

    여기까지 — 규칙 동작 확인
    • /status의 Setting sources에 User settings가 보인다
    • Manual 모드인데 python3 -m json.tool ~/.claude/settings.json이 승인 없이 실행됐다
    • .env 읽기가 막혔다

    셋 중 하나라도 다르면 다음 단계로 가지 말고 4단계의 JSON 검증부터 다시 하세요. 여기까지가 이 모듈의 결과물입니다.

  8. 일부러 JSON을 깨뜨립니다

    실무에서 가장 흔한 실수를 재현합니다. allow 목록의 마지막 항목 뒤에 쉼표를 하나 추가하고 저장하세요. 4-5에서 본 "뒤따르는 쉼표"입니다.

    고칠 부분 (마지막 항목 뒤에 쉼표 추가)
          "Bash(python3 -m json.tool *)",
    ],

    /exit으로 세션을 나온 뒤 claude로 다시 시작합니다. Settings Error 대화상자가 나타나야 정상입니다.

  9. 원인을 확인하고 되돌립니다

    대화상자에서 계속 진행을 고른 뒤, 터미널에서 원인을 확인합니다.

    셸 명령
    claude doctor
python3 -m json.tool ~/.claude/settings.json

    두 번째 명령이 몇 번째 줄이 문제인지 알려 줍니다. 추가했던 쉼표를 지우고 저장한 뒤, 다시 python3 -m json.tool로 JSON OK가 나오는지 확인하세요.

    여기까지 — 고장과 복구
    • Settings Error를 직접 재현했다
    • claude doctor와 JSON 검증으로 원인을 찾았다
    • 쉼표를 지워 원래대로 되돌렸고 JSON OK가 나온다

    이 경험이 중요한 이유는, 실무에서 설정이 "왜 안 먹지" 할 때 대부분 파일이 깨져서 통째로 무시되고 있기 때문입니다.

  10. 1회용 오버라이드를 시험합니다

    파일을 고치지 않고 이번 세션에만 값을 바꿔 봅니다. 명령줄은 파일보다 우선순위가 높습니다(4-3).

    셸 명령
    claude --settings '{"permissions":{"deny":["Read(./README.md)"]}}'

    이 옵션으로 연 세션에서 아래 프롬프트를 보내 막히는지 확인합니다.

    프롬프트
    README.md를 보여 주세요.

    /exit 후 그냥 claude로 다시 시작하면 이 규칙은 사라집니다. 파일에 쓰이지 않기 때문입니다.

  11. 정리하고 최종 확인합니다

    실습용으로 만든 .env를 지웁니다. 개인 설정 파일은 그대로 두어도 됩니다.

    셸 명령 · 예상 출력
    $ cd ~/claude-code-sandbox && rm .env
$ python3 -m json.tool ~/.claude/settings.json > /dev/null && echo "JSON OK"
JSON OK

$ git status --short
 M .gitignore

    .gitignore 변경은 커밋해도 되고 되돌려도 됩니다. 어느 쪽이든 무엇이 바뀌었는지 알고 결정하는 것이 중요합니다.

6. 예제 코드·예제 프롬프트

실습 자료

예제 코드 — 개인 설정 파일 전문

사전 준비물: 홈 디렉터리에 .claude 폴더(없으면 mkdir -p ~/.claude). 기존 파일이 있으면 백업.

~/.claude/settings.json — 발췌가 아닌 전문입니다. 그대로 저장하세요
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git log *)",
      "Bash(git diff *)",
      "Bash(python3 -m json.tool *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

각 규칙을 이렇게 고른 이유:

규칙왜 넣었나
Bash(git status)읽기만 하고 아무것도 바꾸지 않음. 거의 매 세션 쓰임. Claude Code가 이미 내장으로 승인 없이 실행하는 명령이라(4-4) 정책을 명시적으로 남기는 의미
Bash(git log *)위와 같음. *로 옵션을 허용하되 git의 다른 하위 명령은 열지 않음
Bash(git diff *)위와 같음. Bash(git *)로 쓰지 않은 것이 요점 — 그러면 git reset·git push까지 열림
Bash(python3 -m json.tool *)읽기만 하고 아무것도 바꾸지 않는 JSON 검증 명령이지만, 위 세 git 명령과 달리 내장 목록에 없어 원래는 매번 승인이 필요합니다. 설정 파일을 고칠 때마다 검증하는 이 모듈의 흐름과 맞고, allow 규칙의 효과를 직접 눈으로 확인할 수 있어 5단계 프롬프트 A에 씁니다
Read(./.env), Read(./.env.*)자격 증명이 담기는 파일. 모든 프로젝트에 적용해야 하므로 사용자 파일에 둠

예상 출력: 파일 저장만 하므로 출력이 없습니다.

성공 확인 방법: 아래 명령이 JSON OK를 출력하고, 세션에서 /status의 Setting sources에 User settings가 나타나면 성공입니다.

확인 명령
python3 -m json.tool ~/.claude/settings.json > /dev/null && echo "JSON OK"
응답은 매번 다릅니다

아래 두 프롬프트의 "예상 출력"은 응답 예시입니다. 성공 여부는 문구가 아니라 승인 화면이 떴는지 안 떴는지로 판단합니다.

프롬프트 A — allow 규칙 동작 확인

사전 준비물: 설정 파일이 로드된 세션, 상태 표시줄이 ⏸ manual mode on인 상태.

실행할 프롬프트 전문
python3 -m json.tool 명령으로 ~/.claude/settings.json이 유효한 JSON인지 확인해 주세요. 정확히 python3 -m json.tool ~/.claude/settings.json 명령을 실행하면 됩니다.

예상 출력(응답 예시): 설정 파일이 유효한 JSON이라는 답과 함께, 파일 내용이 정리되어 나옵니다.

성공 확인 방법: Manual 모드인데도 승인 화면이 뜨지 않고 바로 실행되면 성공입니다. git status·git log·git diff는 Claude Code가 이미 내장으로 승인을 건너뛰는 명령이라 이 확인에는 쓰지 않습니다 — 자세한 이유는 4-4를 참고하세요. 승인 화면이 떴다면 아래를 확인하세요.

프롬프트 B — deny 규칙 동작 확인

사전 준비물: 프롬프트 A를 보낸 같은 세션, 3단계에서 만든 .env가 있는 상태.

실행할 프롬프트 전문
.env 파일 내용을 보여 주세요.

예상 출력(응답 예시): 해당 파일을 읽을 수 없다는 취지의 답이 나옵니다. 문구는 실행마다 다릅니다.

성공 확인 방법: 파일 내용(API_KEY=...)이 화면에 나타나지 않으면 성공입니다. 내용이 나왔다면 deny 규칙이 적용되지 않은 것이므로, 규칙의 경로 표기(./ 포함 여부)를 다시 확인하세요.

7. 트러블슈팅

설명
증상원인해결
설정을 저장했는데 아무것도 안 바뀐다 JSON이 깨져 파일 전체가 무시됨 python3 -m json.tool ~/.claude/settings.json으로 검증하고, claude doctor로 거부된 항목을 확인합니다. 주석과 뒤따르는 쉼표가 가장 흔한 원인입니다.
/status에 User settings가 안 보인다 경로가 틀렸거나 파일이 없음 정확한 경로는 ~/.claude/settings.json입니다. Windows에서는 %USERPROFILE%\.claude를 뜻합니다.
allow 규칙을 넣었는데 여전히 묻는다 규칙과 실제 명령이 안 맞거나, 상위 파일의 ask·deny가 있음 Claude가 실행하려는 명령을 승인 화면에서 정확히 읽고 규칙과 대조하세요. 조직 관리 설정이 있으면 /status에서 관리 소스를 확인하고 관리자에게 문의합니다.
"Yes, and don't ask again"을 골랐는데도 계속 묻는다 그 선택은 프로젝트 로컬 파일에 allow 규칙을 저장하는데, 거기의 allow는 프로젝트나 관리 파일의 ask 규칙을 이기지 못함 상위 파일에 ask 규칙이 있는지 확인합니다. 팀 정책이라면 임의로 우회하지 말고 팀과 논의하세요. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)
팀 파일에 커밋했는데 팀원에게 적용되지 않는다 permissions.allow는 각 팀원이 폴더를 신뢰해야 적용됨 deny와 ask 규칙은 바로 적용되지만 allow는 신뢰 단계를 기다립니다. 팀원에게 폴더 신뢰 단계를 밟게 하세요. (출처: code.claude.com/docs/en/settings, 2026-08-26 확인)

7-2. 흔한 잘못된 습관

오류가 나지 않아 위 표로는 잡히지 않지만, 그대로 두면 권한 체계가 무너지는 경우입니다.

습관겉으로 나타나는 모습대응
규칙을 넓게 잡는다 승인 화면이 사라져 편해짐. 사고가 나기 전까지는 아무 문제 없어 보임 Bash(git *)가 아니라 Bash(git status)처럼 하위 명령까지 지정합니다. 규칙 하나마다 "잘못 실행되면 되돌릴 수 있나"를 묻습니다(4-4).
"Yes, and don't ask again"으로 규칙을 쌓아 둔다 어느 순간부터 거의 안 물어봄. 무엇을 허용했는지 아무도 기억하지 못함 가끔 .claude/settings.local.json을 열어 쌓인 규칙을 읽고, 의도하지 않은 것을 지웁니다.
설정을 바꾸고 확인하지 않는다 바뀐 줄 알고 일하는데 실제로는 파일이 깨져 전부 무시되는 중 저장 → JSON 검증 → /status 확인을 한 세트로 굳힙니다.
deny를 프로젝트 파일에만 둔다 그 프로젝트는 안전한데, 다른 프로젝트에서는 .env가 그대로 읽힘 모든 프로젝트에 적용해야 하는 보호 규칙은 사용자 파일에 둡니다(4-2).

이번 재검증에서 바로잡은 것

git status·git log·git diff는 Claude Code의 내장 읽기 전용 명령 목록에 포함돼 있어, 커스텀 allow 규칙이 없어도 Manual 모드에서 승인 없이 실행됩니다. 설정 파일을 완전히 지운 상태로 대조군을 실행해 직접 확인했습니다. 이전 버전은 이 세 명령으로 "승인 없이 실행되면 allow 규칙이 동작한 것"이라고 설명했는데, 이는 규칙이 있든 없든 참인 문장이라 증명이 되지 않았습니다. 4-4에 이 사실을 밝히는 콜아웃을 추가하고, 5·6절의 검증 실습을 내장 목록에 없는 Bash(python3 -m json.tool *) 규칙으로 바꿔 실제로 allow 규칙의 효과를 확인하도록 고쳤습니다. (CLI 실행 결과 직접 확인, 2026-08-26 — 출처: code.claude.com/docs/en/permissions의 "Read-only commands" 절)

초급 범위를 넘는 항목(관리 설정 배포, 훅 설정, 모델 목록 병합의 예외 규칙)은 같은 문서에서 확인했으나 이 모듈에서는 다루지 않았습니다.
