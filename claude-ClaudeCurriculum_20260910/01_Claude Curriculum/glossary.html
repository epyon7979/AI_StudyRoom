Glossary

커리큘럼 용어집

이 커리큘럼 전체에서 쓰는 용어를 한 곳에 모읍니다. 프로젝트 공용 문서 1개만 유지하며, 새 용어가 나올 때마다 갱신합니다.

표기 규칙

규칙
  • 제품명은 영문 그대로 씁니다. Claude, Claude Cowork, Claude Design, Claude Code.
  • 기능명은 최초 등장 시 한국어(영문)로 병기하고, 이후에는 하나의 표기로 통일합니다. 예: 커넥터(Connectors).
  • UI의 버튼·메뉴 명칭은 실제 표기 그대로 따옴표로 감쌉니다. 예: "New chat"을 클릭합니다.
  • 한국어 UI 제공 여부가 확인되지 않은 화면은 영문 표기를 기준으로 하고 한국어 설명을 병기합니다.
  • 동일 개념에는 프로젝트 전체에서 하나의 번역어만 사용합니다.
  • 커맨드·파일명·경로는 고정폭으로 표기합니다.
모듈에서 용어집으로 링크하는 방법

모든 용어 행에 고유 id가 있습니다. 모듈 본문에서 <a href="glossary.html#term-cowork">Claude Cowork</a> 형태로 링크하면 해당 용어로 바로 이동합니다.

2. 트랙과 과정 구조

용어정의
트랙track 학습자가 제품을 다루는 방식으로 나눈 3단계 구분. 초급(basic), 중급(custom), 상급(advanced). 주제의 어려움이 아니라 다루는 방식이 기준입니다.
초급 basicbasic 기본 설정(default)을 바꾸지 않고 기본 제공 기능을 사용하는 단계. 전제 지식 없음을 가정하고, 한 단계 = 한 동작으로 분해해 서술합니다. 되돌리기 어려운 명령·옵션은 다루지 않습니다.
중급 customcustom 본인 계정·본인 작업 범위에서 설정과 확장 기능을 커스터마이즈해 개인 업무 워크플로에 맞추는 단계. 동작 원리와 설정 이유를 함께 다룹니다.
상급 advancedadvanced 팀·조직 단위로 표준화·자동화·확산하는 단계. 다른 사람에게 영향을 주거나 관리자 권한·자동 실행이 필요한 범위를 다루며, 설계 판단과 트레이드오프 중심으로 서술합니다.
파트Part 같은 트랙에 속한 4개 코스의 묶음. Part 1은 초급, Part 2는 중급, Part 3은 상급입니다.
코스course 제품 하나 × 트랙 하나의 조합. 총 12개로 고정되어 있으며 늘거나 줄지 않습니다. 각 코스는 1개 이상의 모듈로 구성됩니다.
모듈module 학습 문서 1개 = HTML 파일 1개. 하나의 완결된 결과물을 만드는 단위입니다. 코스별 모듈 수는 사전에 정하지 않고 작성 직전에 결정합니다.

3. 문서 구조와 산출물

용어정의
로드맵index.html 커리큘럼 전체의 코스·모듈 목록과 학습 순서를 담은 문서. 모듈 목록의 유일한 기준이며, 모듈이 추가·분할·삭제되면 즉시 갱신합니다.
용어집glossary.html 이 문서. 프로젝트 전체에서 공용으로 1개만 유지합니다.
모듈 정보module info 모듈 첫머리에 두는 표. 제품, 트랙, 코스 내 번호·제목, 예상 소요 시간, 확인 기준일, 기준 요금제, 기준 버전을 담습니다.
학습 목표learning objectives 모듈당 최대 3개. "~을 할 수 있다" 형태로 씁니다. 3개를 넘으면 모듈을 분할합니다.
사전 준비prerequisites 모듈을 시작하기 전에 갖춰야 할 것. 필요 플랜, 설치 여부, 사전 지식, 예상 사용량을 적습니다.
핵심 개념key concepts 실습 전에 알아야 할 개념 설명. 두괄식으로 무엇·왜를 먼저 쓰고 동작 원리는 뒤에 둡니다.
단계별 실습step-by-step walkthrough 번호가 붙은 실습 절차. 단계마다 캡처 지시서 또는 코드·프롬프트 예시를 최소 1개 포함합니다. 단계가 15개를 넘으면 모듈을 분할합니다.
예제 프롬프트example prompt 학습자가 그대로 복사해 입력하는 프롬프트 전문. 코드와 동일하게 실습 자료로 취급하며, 모델 응답은 실행마다 달라질 수 있음을 함께 표기합니다.
재현성 4요소reproducibility set 모든 실습에 반드시 포함하는 4가지. ① 사전 준비물 ② 실행할 명령·코드 전문 ③ 예상 출력 ④ 성공 확인 방법.
트러블슈팅troubleshooting 실습 중 자주 발생하는 오류 2~5개와 각각의 해결법.
확인 체크리스트checklist 모듈 끝에 두는 3~5문항의 자가 점검 항목. 다음 모듈로 넘어가도 되는지 판단하는 기준입니다.
캡처 지시서capture spec 학습자 또는 작성자가 직접 찍어야 할 화면을 지정한 안내 상자. 화면, 진입 경로, 캡처 범위, 강조 표시, 캡션을 적고 C-01부터 번호를 붙입니다. 모듈 하단 "필요 캡처 목록"에 같은 번호로 다시 정리합니다.
캡처 자리표시screenshot placeholder 실제 이미지가 아직 없는 자리에 두는 점선 박스(.screenshot-placeholder). 나중에 실제 캡처 이미지로 교체합니다. 문서는 자리표시 상태에서도 완결된 형태를 유지해야 합니다.
목업mockup 화면 구성을 HTML·SVG나 텍스트 도식으로 근사 재현한 것. 실제 스크린샷이 아니므로 "실제 화면과 다를 수 있음"을 반드시 함께 표기합니다.
참고 자료references 모듈 본문에서 실제로 사용한 공식 문서·첨부 자료 목록. 문서명, URL(또는 첨부 파일명), 확인 날짜를 함께 적습니다.

4. 상태와 검증 표기

용어정의
코스 상태course status 로드맵에 표기하는 4단계. 미착수 모듈 분할안 없음 · 분할 확정 모듈 개수·제목·범위 확정 · 작성 중 확정 모듈 일부 작성 · 완료 확정 모듈 전부 작성.
진척률progress "완료 모듈 수 / 분할 확정된 모듈 수"로만 표기합니다. 전체 모듈 수는 확정 전까지 표기하지 않습니다.
공식 자료 미확인unverified 공식 자료로 확인하지 못한 항목에 붙이는 표시. 이 경우 값을 임의로 채우지 않습니다. 미확인 표기는 이 문구 하나로 통일합니다.
확인 기준일verified as of 모듈에 담긴 제품 정보를 공식 자료로 확인한 날짜. 모듈 정보 표에 적습니다.
기준 요금제baseline plan 그 모듈을 그대로 따라 하기 위해 필요한 요금제. 모듈 서두에 밝히며, 요금제명과 한도는 작성 시점의 공식 자료로 확인해 적습니다. 관리자 설정으로 기본 비활성인 기능은 그 사실도 함께 적습니다.
기준 버전baseline version 실습에 사용한 CLI·라이브러리 버전과 모델명. 공식 문서에서 확인된 문자열만 씁니다. 버전 지정이 없으면 최신 안정 버전(Stable Release)을 기준으로 하며, Preview·Beta·RC는 안정 버전으로 취급하지 않습니다.
최종 확인일last checked 모든 산출물 하단에 최종 확인일: YYYY-MM-DD 형식으로 적는 날짜. 문서를 손댈 때마다 갱신합니다.

역할 부여의 자리role placement API의 system 파라미터에 해당하는 자리가 claude.ai에는 셋 있습니다 — 프롬프트 안(이 요청만), 계정 지침(모든 대화), 프로젝트 지침(그 프로젝트만). Claude Code에서는 CLAUDE.md·SKILL.md·서브에이전트 프론트매터가 같은 역할을 합니다. 역할이 매번 같으면 지침으로 올리고, 작업마다 다르면 프롬프트에 둡니다.
예시 제시few-shot / multishot prompting 출력 형식·어조·구조를 조종하는 가장 신뢰할 만한 방법 중 하나. 세 기준을 지킵니다 — 적합성(실제 사용 사례를 가깝게 반영), 다양성(엣지 케이스를 덮고 의도치 않은 패턴을 학습하지 않을 만큼), 구조(<example>·<examples>로 감싸 지시와 구별). 3~5개가 최적이며, Claude에게 세트를 평가하게 하거나 추가 생성을 시킬 수 있습니다. (출처: platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, 2026-08-20 확인)
확장 사고 우선 원칙extended thinking over manual CoT 공식 안내상 확장 사고를 쓸 수 있을 때는 수동 사고 유도보다 확장 사고가 일반적으로 낫습니다. 수동 사고 유도가 값어치 있는 것은 ① 확장 사고를 쓸 수 없을 때 ② 검토할 수 있는 투명한 추론이 필요할 때입니다. 후자는 근거를 본문에 남겨 다른 사람에게 보여 줘야 하는 경우입니다. (출처: claude.com/blog/best-practices-for-prompt-engineering, 2026-08-20 확인)
사고 조절steering thinking behavior 사고 발동 동작은 프롬프트로 조절할 수 있습니다. 공식 문서는 이제 사고를 줄이는 방향의 안내를 예시로 제시합니다 — 지침이 크고 복잡하면 모델이 원하는 것보다 자주 생각할 수 있어, "사고는 지연을 늘리므로 답변 품질을 의미 있게 높일 때만" 쓰라고 방향을 잡아 줍니다. 예전의 "Think step-by-step을 붙여 더 생각하게 하라"와 방향이 반대입니다. (출처: platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, 2026-08-20 확인)
프롬프트 자산화prompt as an asset 검증된 프롬프트를 매번 붙여 넣지 않고 계정 지침·프로젝트 지식·스킬에 심어 재사용하는 것. 자산이 되는 순간 세 가지 문제가 새로 생깁니다 — ① 판단 근거가 사라진다 ② 낡는다 ③ 비용이 고정된다. 그래서 검증 기록·갱신 계기·담을 자리를 함께 정해야 합니다. 프롬프트를 기본 취향 / 배경 자료 / 절차와 예시 / 이번 입력 네 조각으로 나눠 각각 다른 그릇에 담는 것이 요점입니다.
검증 기록VERIFICATION.md 프롬프트 자산과 같은 폴더에 두는 사람용 문서. 무엇을 했는지가 아니라 왜 그렇게 했는지를 적습니다 — 검증한 모델, 반복 실행 결과, 예시의 개수·다양성·출처, 설계 판단의 이유, 낡을 지점, 그리고 다음 담당자가 모르면 헤맬 전제. SKILL.md 본문에 넣으면 호출마다 컨텍스트를 차지하므로 별도 파일로 둡니다.
조직 지침 우선 원칙organization instructions take precedence Team·Enterprise의 Admin·Owner·Primary Owner가 설정하는 조직 지침은 조직 전체 모든 대화에 적용되며, 개인 지침과 충돌하면 조직 지침을 따릅니다. 공식 예시 — 조직이 "항상 격식 있는 영어로"라 하고 개인이 "편한 어조로"라 하면 Claude는 격식 있게 답합니다. 즉 개인은 우회할 수 없으므로 조직 지침에는 "좋은 규칙"이 아니라 "모두에게 참인 규칙"만 담아야 합니다. (출처: support.claude.com/en/articles/14546867, 2026-08-20 확인)
파도 배포rolling out in waves 공식 권고 방식. 첫날 모두에게 모든 기능을 열어 주는 것이 예상치 못한 소비를 만드는 가장 빠른 길이므로, 사용 강도가 높은 것은 파도로 나눠 생산적으로 쓸 가능성이 가장 높은 팀부터 배포합니다. 파도마다 다음으로 넘어갈 조건이 정해져 있지 않으면 파도가 아니라 지연입니다. (출처: support.claude.com/en/articles/14782391, 2026-08-20 확인)
되돌리기 절차rollback procedure 조직 배포 계획서의 필수 항목. 네 가지를 채워야 합니다 — 권한자 2명 이상(1명이면 그 사람이 자리에 없을 때 못 끕니다), 구체적 절차("관리자에게 문의"는 절차가 아닙니다), 반영까지 걸리는 시간, 이전 버전 보관 위치. 조직 설정은 개인이 우회할 수 없으므로 사고 시 되돌릴 사람이 없으면 조직 전체가 멈춥니다.
