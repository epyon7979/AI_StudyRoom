2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. 사양서 없는 코드의 현재 동작을 특성화 테스트로 박제할 수 있다.
  2. PostToolUse 훅으로 Edit·Write 변경마다 테스트를 자동 실행하고 결과를 Claude에게 전달할 수 있다.
  3. 특성화 테스트와 훅이 각각 무엇을 못 잡는지 알고 대응할 수 있다.

3. 사전 준비

설명

3-1. 준비물

항목내용

3-2. 이 문서의 표기 방식

상급 01과 같습니다.

3-3. 특성화 테스트는 제품 기능이 아닙니다

일반 소프트웨어 공학 기법입니다

특성화 테스트(characterization test)는 Anthropic 제품의 기능이 아니라 레거시 코드를 다루는 일반 기법입니다. 이 모듈은 그 기법을 Claude Code의 훅과 결합하는 방법을 다룹니다. 제품 쪽 사실(PostToolUse의 동작, 훅 설정)만 공식 문서로 확인했고, 테스트 기법 자체는 이 커리큘럼이 정한 구성입니다.

테스트 프레임워크는 표준 라이브러리 unittest를 씁니다. 사내 표준이 다르면 그것으로 바꿔도 되며, 이 모듈의 구조는 그대로 적용됩니다.

4. 핵심 개념

설명

4-1. 결론부터

레거시에는 "옳은 동작"을 아는 사람이 없습니다. 그래서 옳은 동작이 아니라 지금 동작을 지킵니다. 특성화 테스트는 현재 출력을 그대로 파일로 박제해 두고, 변경 후 결과가 달라지면 알려 줍니다. 버그도 함께 박제되지만 그게 의도입니다 — 지금 목표는 고치는 것이 아니라 모르게 바뀌는 것을 막는 것입니다.

4-2. 모듈 01과 정반대 지점에서 작동합니다

모듈 01 (PreToolUse)이 모듈 (PostToolUse)
시점도구 실행 전도구 실행이 성공한 뒤
할 수 있는 것호출을 차단차단 불가. 이미 실행됨
exit 2의 효과도구 호출 차단Claude에게 stderr를 보여 줄 뿐
쓰임절대 건드리면 안 되는 것건드려도 되지만 깨지면 알아야 하는 것

공식 문서의 이벤트별 표가 이를 명확히 합니다 — PostToolUse는 차단 불가이며 exit 2를 써도 Claude에게 stderr를 보여 줄 뿐, 도구는 이미 실행된 뒤라는 점이 전부입니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

되돌리기는 여전히 사람 몫입니다

이 모듈의 훅은 알려 줄 뿐 되돌리지 않습니다. 되돌릴 수 있는 것은 초급 02에서 배운 git 복구 지점입니다. 안전망은 훅 + git 두 겹이며, 훅만으로는 반쪽입니다.

이 훅은 Edit·Write로 만든 변경만 봅니다 — Bash로 고치면 조용히 통과합니다

matcher는 도구 이름만 봅니다. "Edit|Write"로 등록한 이 훅은 Claude가 Edit·Write 도구를 쓸 때만 실행됩니다. 같은 파일을 Bash의 sed -i나 cat > file 같은 명령으로 고치면 훅 자체가 실행되지 않습니다. 공식 문서가 이를 명시합니다 — matcher: "Edit|Write"로 등록한 PostToolUse 훅은 Bash 명령이나 Claude Code 밖의 다른 프로세스가 같은 파일을 다시 써도 실행되지 않는다고 못 박고 있습니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

이 샌드박스에서 직접 재현했습니다. Claude에게 "Bash의 sed -i만 써서 app.py를 고쳐 달라"고 지시하자 파일은 실제로 깨졌지만, 훅 실행 로그는 한 줄도 남지 않았고 Claude는 실패 언급 없이 "수정 완료했습니다"로 정상 종료했습니다. 그 상태에서 python3 -m unittest discover -s tests -q를 사람이 직접 돌려서야 FAILED를 확인할 수 있었습니다. 실습 12단계에서 같은 과정을 직접 재현합니다.

대응: 무엇으로 바뀌었든 감지하려면 PostToolUse가 아니라 FileChanged 이벤트를 씁니다. 파일시스템을 직접 감시하므로 Bash·외부 프로세스가 고쳐도 실행됩니다. 다만 FileChanged는 decision control이 없어 실패 사유를 Claude에게 구조적으로 넘기지 못하고, 대화형 세션에서 사람에게 터미널 알림만 띄웁니다 (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인). 즉 Bash발 변경까지 잡으려는 순간 "Claude가 스스로 알아채는" 안전망에서 "사람이 알림을 보고 대응하는" 안전망으로 성격이 바뀝니다 — 이 모듈이 만든 훅과는 다른 도구이고, 이 모듈에서는 구현하지 않습니다.

4-3. PostToolUse가 결과를 전달하는 방법

공식 문서의 결정 제어 표에 따르면 PostToolUse는 최상위 decision 패턴을 씁니다 — decision: "block"과 reason입니다. PreToolUse와 달리 이 형식이 지금도 쓰이는 현재 표기입니다(PreToolUse는 같은 최상위 형식이 지금은 hookSpecificOutput.permissionDecision으로 대체됐습니다). (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

방법결과이 모듈에서
{"decision": "block", "reason": "..."}사유가 구조적으로 Claude에게 전달됨사용
exit 2 + stderrstderr가 Claude에게 전달됨대안
exit 0, 출력 없음아무 일 없음테스트 통과 시

훅 출력 문자열은 10,000자로 제한되며 초과분은 파일로 저장되고 미리보기와 경로로 대체됩니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인) 그래서 이 모듈의 훅은 테스트 출력의 마지막 20줄만 전달합니다.

4-4. 특성화 테스트가 못 잡는 것

이 절이 이 모듈에서 가장 중요합니다

골든 케이스가 건드리지 않는 동작 변화는 잡히지 않습니다. 테스트가 통과했다고 아무것도 안 바뀐 것이 아닙니다.

이 샌드박스에서 실제로 확인한 예입니다. 재고가 4·25·7일 때 THRESHOLD를 10에서 15로 바꿔도 테스트는 통과합니다. 두 기준값 사이에 있는 품목이 하나도 없어 출력이 똑같기 때문입니다.

기준값걸리는 품목출력
10 (박제 당시)4, 72줄
15 (변경 후)4, 72줄 — 동일
26이었다면4, 25, 73줄 — 달라져서 잡힘

대응은 두 가지입니다. ① 경계를 건드리는 케이스를 골든에 추가한다. ② 잡히지 않는 영역이 무엇인지 문서에 적어 둔다. 실습 11단계에서 이 판단을 직접 해 봅니다.

4-5. 매 수정마다 도는 비용

PostToolUse 훅은 Edit·Write 도구로 파일을 고칠 때마다 실행됩니다(4-2의 한계 참고 — Bash로 고치면 이 비용도, 검사도 발생하지 않습니다). 테스트가 느리면 작업 전체가 느려집니다.

테스트 소요판단
1초 미만매 수정마다 돌려도 무방
1~5초if 필드로 대상 파일을 좁히거나 빠른 부분집합만 실행
5초 이상매 수정은 포기. Stop 이벤트(턴 종료 시)로 옮기는 것을 검토

이 샌드박스의 테스트는 측정 결과 약 0.14초라 매 수정마다 돌려도 부담이 없습니다. 실제 프로젝트에서는 반드시 측정하고 판단하세요(실습 8단계).

5. 단계별 실습

실습

만들 결과물: 골든 파일로 박제된 특성화 테스트와, Edit·Write 변경마다 자동 실행되는 PostToolUse 훅.

  1. 무엇을 박제할지 정합니다

    박제 대상은 겉으로 관찰 가능한 동작입니다. 내부 구현이 아니라 입력을 넣었을 때 나오는 것을 잡습니다.

    셸 명령 — 현재 동작 훑어보기
    cd ~/claude-code-sandbox
python3 app.py inventory.csv
python3 app.py inventory.csv 30
python3 app.py

    이 실습에서는 정상 실행 3가지 + 인자 없음 + 없는 파일 5가지를 박제합니다. 오류 상황도 현재 동작이므로 함께 박제합니다.

  2. 케이스 정의와 실행기를 만듭니다

    6번 절 예제 ①을 tests/cases.py에 저장합니다. 테스트와 캡처 스크립트가 같은 정의를 공유하게 만드는 것이 요점입니다.

    셸 명령
    mkdir -p tests/golden
  3. 골든 캡처 스크립트를 만들고 실행합니다

    6번 절 예제 ②를 tests/capture_golden.py에 저장하고 실행합니다.

    셸 명령 · 예상 출력
    $ python3 tests/capture_golden.py
박제: default.txt (83바이트)
박제: threshold_30.txt (103바이트)
박제: threshold_5.txt (59바이트)
박제: no_args.txt (82바이트)
박제: missing_file.txt (51바이트)

골든 5건을 .../tests/golden에 저장했습니다.

    바이트 수는 환경에 따라 다를 수 있습니다. 5건이 만들어졌는지가 확인 기준입니다.

  4. 박제된 내용을 직접 읽습니다

    이 단계를 건너뛰지 마세요. 골든 파일은 앞으로 "정답"으로 취급됩니다. 무엇이 정답이 됐는지 눈으로 확인해야 합니다.

    셸 명령 · 예상 출력
    $ cat tests/golden/default.txt
exit=0
--- stdout ---
[재고 부족] A4 용지 - 현재 4개
[재고 부족] USB 케이블 - 현재 7개
--- stderr ---

    지금 이 동작이 옳은지 아닌지는 판단하지 않습니다. 옳든 그르든 이것이 현재 동작이고, 우리는 이것이 모르게 바뀌는 것을 막으려는 것입니다(4-1).

  5. 테스트를 만들고 통과를 확인합니다

    6번 절 예제 ③을 tests/test_characterization.py에 저장하고 실행합니다.

    셸 명령 · 예상 출력
    $ python3 -m unittest discover -s tests -q
----------------------------------------------------------------------
Ran 5 tests in 0.110s

OK
    여기까지 — 박제
    • 골든 5건이 만들어졌다
    • 골든 내용을 직접 읽어 무엇이 정답이 됐는지 안다
    • 테스트가 OK로 통과한다

    테스트가 실패한다면 골든을 캡처한 뒤에 코드가 바뀐 것입니다. 코드를 되돌리거나 골든을 다시 캡처하세요.

  6. 변경 감지가 실제로 되는지 시험합니다

    일부러 동작을 바꿔 봅니다. app.py의 사용법 문구를 한국어로 바꾸고 테스트를 돌립니다.

    고칠 부분
        print("사용법: python3 app.py <csv 경로> [기준값]")
    셸 명령 · 예상 출력
    $ python3 -m unittest discover -s tests -q
[no_args] 현재 동작이 박제된 동작과 다릅니다.
----------------------------------------------------------------------
Ran 5 tests in 0.095s

FAILED (failures=1)

    확인 후 git restore app.py로 되돌립니다.

  7. 잡히지 않는 변경도 시험합니다

    이번에는 4-4의 사례를 직접 겪어 봅니다. THRESHOLD를 10에서 15로 바꾸고 테스트를 돌립니다.

    셸 명령 · 예상 출력
    $ python3 -m unittest discover -s tests -q
----------------------------------------------------------------------
Ran 5 tests in 0.095s

OK
    기준값이 바뀌었는데 테스트는 통과했습니다

    재고가 4·25·7이라 10과 15 사이에 품목이 없어 출력이 같습니다. 테스트 통과 = 아무것도 안 바뀜이 아닙니다. 확인 후 되돌리세요.

  8. 테스트 실행 시간을 측정합니다

    훅으로 자동화하기 전에 비용을 먼저 재 봅니다(4-5).

    셸 명령 · 예상 출력
    $ git restore app.py
$ time python3 -m unittest discover -s tests -q

real    0m0.1xx s

    1초 미만이면 매 수정마다 돌려도 됩니다. 그보다 느리면 4-5의 표로 판단하세요.

  9. 훅 스크립트를 만들고 단독 검증합니다

    6번 절 예제 ④를 .claude/hooks/run-characterization.py에 저장하고 실행 권한을 줍니다. 상급 01에서 배운 대로 등록 전에 단독으로 시험합니다.

    셸 명령 · 예상 출력 (테스트가 통과하는 상태)
    $ chmod +x .claude/hooks/run-characterization.py
$ echo '{"tool_name":"Edit","tool_input":{"file_path":"app.py"}}' \
    | CLAUDE_PROJECT_DIR=$(pwd) python3 .claude/hooks/run-characterization.py
(출력 없음)

    이제 일부러 깨뜨린 상태에서도 시험합니다. 6단계처럼 사용법 문구를 바꾼 뒤 같은 명령을 실행하면 {"decision": "block", ...} JSON이 나와야 합니다. 확인 후 되돌리세요.

  10. settings.json에 등록하고 실동작을 확인합니다

    6번 절 예제 ⑤로 .claude/settings.json을 갱신합니다. 상급 01의 PreToolUse 훅은 그대로 두고 PostToolUse를 추가합니다.

    세션에서 /hooks로 두 이벤트가 모두 보이는지 확인한 뒤, 프롬프트 A로 일부러 동작을 바꿔 봅니다.

    [캡처 C-01]
    화면
    특성화 테스트 실패가 Claude에게 전달된 대화
    진입 경로
    프롬프트 A 전송 후 훅이 실패를 보고한 시점
    캡처 범위
    실패 사유와 Claude의 반응이 함께 보이는 범위
    강조 표시
    "박제된 동작과 달라졌습니다" 문구(빨간 테두리)

"""특성화 테스트의 실행 케이스 정의. 테스트와 캡처가 공유한다."""
import pathlib
import subprocess
import sys

ROOT = pathlib.Path(__file__).resolve().parents[1]
GOLDEN = pathlib.Path(__file__).parent / "golden"

CASES = {
    "default": ["inventory.csv"],
    "threshold_30": ["inventory.csv", "30"],
    "threshold_5": ["inventory.csv", "5"],
    "no_args": [],
    "missing_file": ["nope.csv"],
}


def run_app(args):
    r = subprocess.run([sys.executable, "app.py", *args],
                       cwd=ROOT, capture_output=True, text=True)
    err = r.stderr
    if err:
        err = err.split("Traceback")[0] + ("Traceback(생략)\n" if "Traceback" in err else "")
    return f"exit={r.returncode}\n--- stdout ---\n{r.stdout}--- stderr ---\n{err}"

#!/usr/bin/env python3
"""특성화 테스트: 현재 동작을 박제해 두고 달라지면 알린다.
'옳은 동작'이 아니라 '지금 동작'을 지킨다."""
import unittest

from cases import CASES, GOLDEN, run_app


class Characterization(unittest.TestCase):
    pass


def _make(name, args):
    def test(self):
        golden = GOLDEN / f"{name}.txt"
        if not golden.exists():
            self.fail(f"골든 파일 없음: {golden}\n"
                      f"tests/capture_golden.py를 먼저 실행하세요.")
        expected = golden.read_text(encoding="utf-8")
        actual = run_app(args)
        self.assertEqual(expected, actual,
                         f"\n[{name}] 현재 동작이 박제된 동작과 다릅니다.")
    return test


for _n, _a in CASES.items():
    setattr(Characterization, f"test_{_n}", _make(_n, _a))


if __name__ == "__main__":
    unittest.main(verbosity=2)

#!/usr/bin/env python3
"""PostToolUse 훅: 파일 수정 후 특성화 테스트를 돌려 동작 변화를 알린다."""
import json
import os
import subprocess
import sys

MAX_LINES = 20


def main():
    try:
        json.load(sys.stdin)
    except Exception:
        return 0

    root = os.environ.get("CLAUDE_PROJECT_DIR") or os.getcwd()
    r = subprocess.run(
        [sys.executable, "-m", "unittest", "discover", "-s", "tests", "-q"],
        cwd=root, capture_output=True, text=True,
    )
    if r.returncode == 0:
        return 0

    detail = (r.stderr or r.stdout).strip().splitlines()
    tail = "\n".join(detail[-MAX_LINES:])
    json.dump({
        "decision": "block",
        "reason": (
            "특성화 테스트가 실패했습니다. 방금 변경으로 현재 동작이 박제된 동작과 달라졌습니다.\n\n"
            + tail
            + "\n\n의도한 변경이면 사용자에게 확인을 받은 뒤 tests/capture_golden.py로 골든을 갱신하세요. "
              "의도한 변경이 아니면 방금 수정을 되돌리세요. 확인 없이 골든을 갱신하지 마세요."
        ),
    }, sys.stdout, ensure_ascii=False)
    return 0


if __name__ == "__main__":
    sys.exit(main())
설계 판단이유
마지막 20줄만 전달훅 출력은 10,000자 제한이 있습니다(4-3)
사유에 "확인 없이 골든을 갱신하지 마세요" 명시Claude가 손쉬운 해결책으로 골든을 덮어쓰면 안전망이 무너집니다
CLAUDE_PROJECT_DIR 사용작업 디렉터리가 어디든 프로젝트 루트에서 테스트를 돌립니다
통과 시 아무것도 출력하지 않음정상일 때 조용해야 실패가 눈에 띕니다
입력 파싱 실패 시 0훅이 죽어 세션을 어지럽히지 않게 합니다

예상 출력: 테스트 통과 시 출력 없음. 실패 시 decision과 reason이 담긴 JSON 한 줄.

Bash 툴로 sed -i 명령을 직접 실행해서 app.py의 사용법 안내를 한국어로
바꿔 주세요. Edit 툴이나 Write 툴은 쓰지 말고 반드시 Bash의 sed -i만
사용하세요.

예상 출력(응답 예시): Claude가 sed -i로 파일을 고치고 "수정 완료했습니다" 같은 정상 종료 메시지를 보여줍니다. 이 샌드박스에서 2026-08-26에 Claude Code CLI v2.1.246으로 직접 실행했을 때 나온 실제 응답은 다음과 같았습니다.

`app.py` 11번째 줄을 `sed -i`로 수정 완료했습니다. `Usage: ...` 문구가
`사용법: python3 app.py <csv 경로> [기준값]`로 바뀌었습니다.

정확한 문구는 실행마다 다릅니다. 확인 기준은 문구가 아니라 테스트·골든 언급이 있는지 없는지입니다.

성공 확인 방법: 아래 2가지를 모두 확인합니다.

7. 트러블슈팅

설명
증상원인해결
테스트가 환경마다 다르게 실패한다 골든에 경로·시간·트레이스백 같은 환경 의존 값이 들어감 예제 ①처럼 축약하거나 제거합니다. 가짜 실패가 반복되면 팀이 안전망을 꺼 버립니다.
골든 파일이 없다는 실패가 난다 캡처를 먼저 실행하지 않음 python3 tests/capture_golden.py를 실행합니다. 커밋 시 tests/golden/이 .gitignore에 걸리지 않았는지도 확인하세요.
훅이 반응하지 않는다 경로 오타·실행 권한·JSON 오류 상급 01의 7번 절과 원인이 같습니다. /hooks에 PostToolUse가 보이는지부터 확인하세요.
Bash로 고쳤는데 훅이 아예 반응하지 않는다 matcher: "Edit|Write"는 도구 이름만 봅니다. Bash로 만든 변경은 애초에 대상이 아닙니다(4-2, 12단계) 이것은 오류가 아니라 이 훅의 설계상 한계입니다. Bash발 변경까지 잡으려면 FileChanged 이벤트를 추가하세요. 단, FileChanged는 decision control이 없어 Claude에게는 전달되지 않고 사람에게만 터미널 알림이 뜹니다 (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인).
훅 때문에 작업이 눈에 띄게 느려졌다 테스트가 매 수정마다 도는 비용 4-5의 표로 판단합니다. if 필드로 대상 파일을 좁히거나("Edit(app.py)") 더 느리면 Stop 이벤트로 옮기는 것을 검토합니다.
Claude가 골든을 갱신해 테스트를 통과시켰다 훅의 사유에 금지 문구가 없거나 약함 예제 ④의 마지막 문장("확인 없이 골든을 갱신하지 마세요")이 들어갔는지 확인합니다. 반복되면 tests/golden/을 상급 01의 PreToolUse 훅 보호 대상에 추가하세요.

7-2. 흔한 잘못된 습관

습관겉으로 나타나는 모습대응
테스트가 빨간불이면 골든부터 갱신한다 즉시 초록불이 됨. 안전망이 스스로를 껐다 골든 갱신은 의도한 변경임을 사람이 확인한 뒤에만 합니다. 커밋에서 tests/golden/이 함께 바뀌었으면 리뷰에서 반드시 이유를 묻습니다.
박제된 내용을 읽지 않는다 잘 돌아감. 나중에 "이게 정답이었어?"를 뒤늦게 발견 캡처 직후 골든을 직접 읽습니다(4단계). 무엇이 정답이 됐는지 모르는 안전망은 위험합니다.
테스트 통과를 "안 바뀜"으로 읽는다 안심하고 넘어감. 골든이 안 건드리는 영역은 조용히 바뀜 못 잡는 영역을 문서에 명시합니다(11단계). 모르는 사각지대보다 아는 사각지대가 낫습니다.
커버리지를 늘리려 케이스를 계속 추가한다 꼼꼼해 보임. 테스트가 느려지고 골든 갱신이 잦아져 결국 아무도 안 봄 특성화 테스트의 목적은 커버리지가 아니라 변경 감지입니다. 4-5의 시간 기준 안에서 유지하세요.

PostToolUse가 차단하지 못하고 exit 2로도 stderr를 Claude에게 보여 줄 뿐이라는 점, 결정 제어가 최상위 decision·reason 패턴이라는 점, 훅 출력이 10,000자로 제한된다는 점, matcher가 도구 이름만 본다는 점과 if 필드의 동작을 공식 훅 문서로 확인했습니다. 2026-08-26 재검증에서 matcher: "Edit|Write"는 Bash가 같은 파일을 고쳐도 실행되지 않는다는 점(공식 문서로 확인, 4-2)과 그 대안인 FileChanged가 decision control이 없어 Claude에게는 전달되지 않는다는 점을 추가로 확인해 반영했습니다.

특성화 테스트는 Anthropic 제품 기능이 아니라 일반 소프트웨어 공학 기법이며, 이 모듈의 테스트 구성은 커리큘럼이 정한 것입니다(3-3). 예제 코드 5종과 훅·settings.json은 2026-08-26에 Claude Code CLI v2.1.246으로 골든 캡처(5건)·통과·실패 감지·경계값 미탐지·훅 단독 검증(통과/차단 양쪽)을 모두 직접 실행해 확인했습니다. 실제 세션에서는 claude -p --output-format stream-json --verbose로 두 가지를 재현했습니다 — ① Edit 도구로 고쳤을 때 PostToolUse 훅이 decision: "block"을 반환하고 Claude가 같은 턴에서 그 사유를 읽고 골든 갱신 여부를 되물은 것(4-3, 10단계, 체크리스트 b4~b6), ② Bash의 sed -i로 같은 파일을 고쳤을 때는 훅이 한 번도 호출되지 않아 Claude도 사람도 실패를 알지 못한 것(4-2, 12단계, 체크리스트 b7~b8). 4-4의 "잡히지 않는 변경" 사례도 실제로 재현해 확인했습니다.
