훅으로 위험 경로 차단하기

CLAUDE.md는 "하지 마세요"라고 부탁합니다. 훅은 실제로 막습니다. 다만 훅도 조용히 꺼질 수 있으므로, 이 모듈의 절반은 훅이 살아 있는지 검증하는 방법에 씁니다.

2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. PreToolUse 훅을 작성해 settings.json에 등록하고 위험한 동작을 차단할 수 있다.
  2. 훅이 조용히 무력화되는 경우를 알고, 게이트가 살아 있는지 검증할 수 있다.
  3. 훅과 권한 규칙 중 무엇으로 강제할지 판단할 수 있다.

3. 사전 준비

설명

3-1. 준비물

항목내용
필요 플랜Pro 또는 Max.
사전 지식Claude Code 중급 5개 모듈 전부 수료. 특히 중급 02의 설정 파일 우선순위와 중급 01의 docs/HANDOVER.md를 씁니다.
실습 대상중급에서 써 온 같은 샌드박스. docs/HANDOVER.md가 있어야 합니다.

예상 사용량프롬프트 3회. 대부분 스크립트 작성과 검증입니다.

3-2. 이 문서의 표기 방식

중급과 같습니다. 커맨드·JSON 키·이벤트 이름은 영문 원문 그대로 싣고 설명만 한국어로 씁니다.

3-3. 공식 예제 대신 python3를 쓰는 이유

의존성을 하나라도 줄입니다

공식 가이드의 Bash 예제들은 JSON 파싱에 jq를 쓰며, 트러블슈팅 절에는 jq가 없으면 "jq: command not found"로 실패한다는 안내까지 있습니다. (출처: code.claude.com/docs/en/hooks-guide, 2026-08-26 확인)

이 모듈은 python3를 씁니다. 샌드박스가 이미 python3를 쓰고 있어 새 의존성이 생기지 않기 때문입니다. 훅의 의존성이 하나 늘면 그것이 없는 환경에서 게이트가 조용히 꺼집니다(4-5). 실제로 이 교재를 만들면서 jq가 없는 환경에서 차단이 통째로 실패하는 것을 확인했습니다.

4. 핵심 개념

설명

4-1. 결론부터

초급 04에서 CLAUDE.md는 강제가 아니라 컨텍스트라고 했습니다. 중급 02에서는 permissions.deny로 규칙을 만들었지만 정적인 경로 패턴만 가능했습니다. 훅은 그 빈자리를 메웁니다 — Claude Code 생애주기의 특정 지점에서 자동으로 실행되는 사용자 정의 처리기이며, 스크립트가 상황을 보고 판단해서 막을 수 있습니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

수단강제력판단어디서 배웠나
CLAUDE.md없음 (부탁)모델이 함초급 04
permissions.deny있음정적 패턴만중급 02

4-2. 훅은 세 겹으로 구성됩니다

설정의 중첩 구조가 정확히 세 단계입니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

단계정하는 것이 모듈의 값
① 이벤트생애주기의 어느 지점PreToolUse (도구 실행 전)
② 매처 그룹언제 발동할지 거르기Edit|Write (파일 수정 도구만)
③ 처리기무엇을 실행할지python3 스크립트
매처 밖의 경로는 그대로 열려 있습니다

"matcher": "Edit|Write"는 Edit·Write 도구 호출만 가로챕니다. Claude는 같은 파일을 Bash 도구의 셸 명령(echo, sed -i, 리다이렉트 등)으로도 고칠 수 있는데, 이 매처는 그 경로를 전혀 보지 않습니다. 공식 가이드도 Claude가 셸 명령으로 파일을 만들거나 고칠 수 있다는 점을 지적하며, 모든 변경을 잡으려면 Bash|PowerShell도 함께 매칭하라고 권합니다. (출처: code.claude.com/docs/en/hooks-guide, 2026-08-26 확인)

실제로 이 모듈의 예제 훅(6번 절)을 그대로 등록한 뒤 "Bash 도구로 utils/formatter.py 끝에 한 줄을 추가해줘, Edit 도구는 쓰지 마"라고 시켰더니 차단되지 않고 파일이 그대로 바뀌었습니다. (CLI 실행 결과 직접 확인, 2026-08-26) 완전히 막으려면 매처를 Edit|Write|Bash로 넓히고, 스크립트에서 tool_name이 Bash일 때는 tool_input.command 문자열에 보호 대상 경로가 들어 있는지 검사하도록 확장해야 합니다 — 이 확장 자체는 이 모듈 범위 밖입니다.

4-3. 어디에 두느냐가 적용 범위를 정합니다

위치범위공유
~/.claude/settings.json내 모든 프로젝트안 됨. 이 기기에만
.claude/settings.json이 프로젝트커밋하면 팀 전체 — 이 모듈이 씀
.claude/settings.local.json이 프로젝트안 됨
관리 정책 설정조직 전체관리자 전용 — 이 코스에서 실습하지 않음
플러그인 / 스킬 / 서브에이전트해당 기능이 켜진 동안모듈 03 이후
훅은 덮어쓰지 않고 합쳐집니다

설정 단계마다의 훅 항목은 서로를 대체하지 않고 합쳐집니다. 사용자·프로젝트·로컬·플러그인 설정은 각자의 훅을 더할 뿐 관리 설정의 훅을 지우지 못하며, 같은 처리기가 여러 파일에 중복 등록되면 한 번만 실행되도록 걸러집니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인) 중급 02에서 배운 permissions.allow 목록 병합과 같은 원리입니다.

4-4. 매처는 문자에 따라 해석이 달라집니다

매처 값해석
"*", "", 생략전부 일치
영문·숫자·_·-·공백·,·|만정확한 문자열 또는 |·,로 구분한 목록
그 밖의 문자 포함정규식 (앵커 없음)
앵커 없는 정규식이 함정입니다

정규식 경로에서는 RegExp.prototype.test로 검사하므로 값 어디에서든 일치하면 성공합니다. Edit.*는 Edit뿐 아니라 NotebookEdit에도 걸립니다. 전체 일치가 필요하면 ^Edit$처럼 감싸세요. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

쉼표 구분과 앞뒤 공백 허용은 v2.1.191 이상, 정확 일치 집합의 하이픈은 v2.1.195 이상이 필요합니다. 그 이전 버전에서 code-reviewer는 앵커 없는 정규식으로 취급되어 senior-code-reviewer에도 발동합니다. (출처: code.claude.com/docs/en/hooks, code.claude.com/docs/en/hooks-guide, 2026-08-26 확인) 이 모듈은 v2.1.246 샌드박스에서 확인했으므로 두 버전 요건을 모두 만족합니다.

4-5. 훅이 조용히 무력화되는 3가지 경우

이 절이 이 모듈에서 가장 중요합니다

훅을 걸었다고 안전해지지 않습니다. 공식 문서가 직접 경고하는 세 가지입니다.

경우공식 문서의 서술결과
① 종료 코드 오해 대부분의 이벤트에서 코드만으로 차단하는 것은 exit 2뿐입니다. stdout에 유효한 JSON이 없으면 exit 1은 유닉스 관례상 실패 코드인데도 차단하지 않는 오류로 처리되어 동작이 진행됩니다. 정책을 강제하려는 훅이면 exit 2를 쓰세요. 막은 줄 알았는데 통과
② 경로 오타 스크립트 경로가 없거나 실행 권한이 없으면 셸이 127 같은 코드로 끝나고 차단하지 않는 오류가 됩니다. 정책 훅을 설정했다면 첫 실행에서 이 알림이 뜨는지 지켜보세요 — settings.json의 오타 하나가 게이트를 조용히 꺼 놓습니다. 게이트가 처음부터 꺼져 있음
③ 타임아웃 타임아웃에 걸린 command·http·mcp_tool 훅은 도구 호출을 막지 않습니다. 호출은 정상 권한 흐름으로 계속되므로, 멈춰 버린 훅이 게이트 역할을 하리라 기대하지 마세요. 느린 훅 = 없는 훅

위 세 서술은 모두 공식 문서에 있습니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인) 그래서 이 모듈의 실습은 스크립트를 단독으로 시험하는 단계(4단계)와 조용한 실패를 일부러 재현하는 단계(9단계)를 반드시 거칩니다.

4-6. 하드 차단은 권한 시스템으로

공식 문서의 권고를 그대로 옮깁니다

처리기의 if 필드는 Bash 명령을 파싱하지 못하면 패턴과 무관하게 훅을 실행하는 쪽으로 열립니다(fail open). if 필터는 최선 노력(best-effort)이므로, 하드한 허용·거부를 강제하려면 훅이 아니라 권한 시스템을 쓰라고 공식 문서가 권고합니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

즉 중급 02의 permissions.deny와 이 모듈의 훅은 경쟁 관계가 아니라 조합입니다. 정적으로 표현 가능한 것은 deny 규칙으로 못 박고, 상황 판단이 필요한 것만 훅으로 처리하세요.

PreToolUse의 deny는 bypassPermissions도 뚫고 유지됩니다

2026-08-20 확인 때는 bypassPermissions 모드에서도 훅의 거부가 유지되는지 공식 문서에서 찾지 못해 공식 자료 미확인으로 남겼습니다. 이번 확인에서 근거를 찾았습니다 — PreToolUse 훅은 dontAsk를 포함한 모든 권한 모드에서 권한 모드 검사보다 먼저 실행되며, permissionDecision: "deny"는 bypassPermissions 모드나 --dangerously-skip-permissions로 시작한 세션에서도 도구 호출을 막습니다. 사용자가 권한 모드를 바꿔서 정책을 우회할 수 없게 하려는 설계입니다. (출처: code.claude.com/docs/en/hooks-guide, 2026-08-26 확인)

이 모듈의 예제 훅을 등록한 채 --dangerously-skip-permissions로 세션을 켜고 프롬프트 A를 다시 보내 실제로 차단되는 것을 직접 확인했습니다 — 거부 사유가 그대로 전달됐고 git status에도 변경이 없었습니다. (CLI 실행 결과 직접 확인, 2026-08-26)

반대 방향은 성립하지 않습니다. 훅이 "allow"를 반환해도 permissions.deny 규칙이나 조직이 ask로 지정한 커넥터·MCP 도구의 승인 요구는 건너뛰지 못합니다. 훅은 제약을 좁힐 수는 있어도, permissions 규칙이 허용한 범위보다 넓힐 수는 없습니다. (출처: code.claude.com/docs/en/hooks-guide, 2026-08-26 확인)

5. 단계별 실습

실습

만들 결과물: 동작이 검증된 차단 훅 1개(스크립트 + 설정)와, 조용한 실패를 재현·복구한 기록.

  1. 무엇을 막을지 정합니다

    중급 01에서 만든 문서를 엽니다. [FACT]로 확인된 규칙 중 어겨지면 되돌리기 어려운 것이 훅의 대상입니다.

    셸 명령
    cd ~/claude-code-sandbox
grep -n 'FACT' docs/HANDOVER.md

    이 실습에서는 utils/formatter.py의 출력 형식 보호를 대상으로 삼습니다. 중급 04의 리뷰 스킬은 이것을 지적했지만, 훅은 Edit·Write 도구로의 수정은 아예 못 하게 합니다. 이 보호가 어디까지인지(예: Bash로는 여전히 우회할 수 있다는 점)는 4-2의 콜아웃에서 바로 확인하세요.

    [WEAK]·[GUESS]는 훅으로 만들지 마세요

    확인되지 않은 규칙을 강제하면 정당한 작업까지 막힙니다. 훅은 확인된 것만 대상으로 합니다.

  2. 훅 스크립트를 작성합니다

    6번 절의 스크립트 전문을 .claude/hooks/protect-formatter.py에 저장합니다.

    셸 명령 (디렉터리 생성)
    mkdir -p .claude/hooks
  3. 실행 권한을 줍니다
    셸 명령 (macOS · Linux · WSL)
    chmod +x .claude/hooks/protect-formatter.py

    Windows에서 Git Bash를 쓰는 경우에도 같은 명령이 동작합니다. 이 단계를 빠뜨리면 4-5의 ②번 조용한 실패가 그대로 발생합니다.

  4. Claude Code를 켜기 전에 스크립트를 단독으로 시험합니다

    이 단계를 건너뛰면 안 됩니다. 가짜 JSON을 파이프로 넣어 스크립트만 따로 검증합니다. 6번 절의 검증 스크립트를 씁니다.

    셸 명령 · 예상 출력
    $ python3 .claude/hooks/verify-hook.py
OK 보호 대상(POSIX)           차단=True (기대=True)
OK 보호 대상(Windows)         차단=True (기대=True)
OK 보호 대상(상대경로)            차단=True (기대=True)
OK 다른 파일                  차단=False (기대=False)
OK file_path 없음           차단=False (기대=False)
OK 비슷한 이름                 차단=False (기대=False)
OK 잘못된 입력                 죽지 않음=True

전체: ALL PASS

    한글 라벨 길이에 따라 차단= 앞 공백 수가 줄마다 다르게 보입니다 — f'{name:22s}'가 터미널 표시 폭이 아니라 문자 수 기준으로 채우기 때문입니다(한글 1글자는 터미널에서 2칸을 차지). 실제로 실행해 한 글자도 다르지 않게 확인한 출력입니다. (CLI 실행 결과 직접 확인, 2026-08-26) 줄이 다르게 보여도 모든 줄이 OK로 시작하고 마지막이 ALL PASS면 정상입니다 — 확인 기준은 정렬이 아니라 이 두 가지입니다.

    여기까지 — 스크립트 검증
    • 스크립트가 실행 권한을 가진다
    • 보호 대상 3가지 표기(절대·Windows·상대)를 모두 차단한다
    • 보호 대상이 아닌 것은 통과시킨다 (특히 formatter_test.py 같은 비슷한 이름)
    • 잘못된 입력에도 죽지 않는다

    하나라도 어긋나면 Claude Code에 등록하지 마세요. 여기서 안 되는 것은 등록해도 안 됩니다.

예제 코드 ① — 훅 스크립트 전문

사전 준비물: ~/claude-code-sandbox/.claude/hooks/ 디렉터리, python3. 외부 패키지는 필요 없습니다.

.claude/hooks/protect-formatter.py — 발췌가 아닌 전문입니다
#!/usr/bin/env python3
"""PreToolUse 훅: 보호 대상 파일의 수정을 차단한다."""
import json
import sys

PROTECTED = ("utils/formatter.py",)
REASON = (
    "utils/formatter.py의 출력 문구 형식은 다른 시스템이 파싱합니다. "
    "변경이 필요하면 docs/HANDOVER.md를 확인하고 담당자와 합의한 뒤 훅을 임시 해제하세요."
)


def main():
    try:
        data = json.load(sys.stdin)
    except Exception:
        # 입력을 못 읽으면 판단하지 않는다(정상 권한 흐름으로 넘김)
        return 0

    path = (data.get("tool_input") or {}).get("file_path") or ""
    norm = path.replace("\\", "/")

    if any(norm.endswith(p) for p in PROTECTED):
        json.dump({
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": REASON,
            }
        }, sys.stdout, ensure_ascii=False)
        return 0
    return 0


if __name__ == "__main__":
    sys.exit(main())

설계 판단을 이렇게 했습니다:

선택이유
permissionDecision: "deny" (exit 2 아님)거부 사유를 구조적으로 전달할 수 있습니다. exit 2도 차단하지만 사유는 stderr로만 갑니다
판단하지 않을 때 아무것도 출력하지 않고 0으로 종료공식 문서에 따르면 PreToolUse 훅이 exit 0으로 끝나는 것은 도구 호출을 승인한다는 뜻이 아니며, 정상 권한 흐름(권한 규칙·사용자 승인)이 그대로 적용됩니다 (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)
입력 파싱 실패 시에도 0훅이 죽어 세션을 막는 것보다 낫습니다. 대신 그만큼 게이트가 열린다는 점을 알고 4단계에서 검증합니다
replace("\\", "/")Windows 경로 구분자를 정규화합니다. 이 한 줄이 없으면 Windows에서 게이트가 열립니다
endswith 사용절대·상대 경로를 모두 잡습니다. 다만 formatter_test.py는 걸리지 않아야 하므로 4단계에서 반드시 확인합니다

예상 출력: 파일 저장이라 출력이 없습니다.

성공 확인 방법: 아래 예제 코드 ②의 검증 스크립트가 ALL PASS를 출력하면 성공입니다.

예제 코드 ② — 훅 검증 스크립트 전문

사전 준비물: 예제 코드 ①이 저장된 상태.

.claude/hooks/verify-hook.py — 발췌가 아닌 전문입니다
#!/usr/bin/env python3
"""훅 스크립트를 Claude Code 없이 단독 검증한다."""
import json
import subprocess
import sys

HOOK = ".claude/hooks/protect-formatter.py"

CASES = [
    ("보호 대상(POSIX)",   {"tool_name": "Edit",  "tool_input": {"file_path": "/home/u/sbx/utils/formatter.py"}}, True),
    ("보호 대상(Windows)", {"tool_name": "Write", "tool_input": {"file_path": "C:\\proj\\utils\\formatter.py"}}, True),
    ("보호 대상(상대경로)", {"tool_name": "Edit",  "tool_input": {"file_path": "utils/formatter.py"}}, True),
    ("다른 파일",          {"tool_name": "Edit",  "tool_input": {"file_path": "/home/u/sbx/app.py"}}, False),
    ("file_path 없음",     {"tool_name": "Bash",  "tool_input": {"command": "ls"}}, False),
    ("비슷한 이름",        {"tool_name": "Edit",  "tool_input": {"file_path": "utils/formatter_test.py"}}, False),
]


def run(payload):
    r = subprocess.run([sys.executable, HOOK], input=json.dumps(payload),
                       capture_output=True, text=True)
    return ("deny" in r.stdout), r.returncode


def main():
    ok = True
    for name, payload, should_block in CASES:
        blocked, code = run(payload)
        good = blocked == should_block
        ok = ok and good
        print(f'{"OK " if good else "!! "}{name:22s} 차단={blocked} (기대={should_block})')

    r = subprocess.run([sys.executable, HOOK], input="not json",
                       capture_output=True, text=True)
    alive = r.returncode == 0
    ok = ok and alive
    print(f'{"OK " if alive else "!! "}{"잘못된 입력":22s} 죽지 않음={alive}')

    print()
    print("전체:", "ALL PASS" if ok else "실패 있음")
    return 0 if ok else 1


if __name__ == "__main__":
    sys.exit(main())

예상 출력: 7줄의 결과와 전체: ALL PASS.

성공 확인 방법: 모든 줄이 OK로 시작하면 성공입니다. 하나라도 !!이면 훅을 등록하지 말고 스크립트를 먼저 고칩니다.

이 검증 스크립트가 이 모듈의 진짜 산출물입니다

훅은 나중에 조용히 망가집니다. 파이썬 버전이 바뀌거나, 보호 대상 경로가 이동하거나, 누군가 스크립트를 건드리면요. 검증 스크립트를 함께 커밋해 두면 언제든 게이트가 살아 있는지 1초 만에 확인할 수 있습니다.

"statusMessage"훅이 도는 동안 사용자에게 보입니다. 게이트가 살아 있다는 신호가 되어 조용한 실패를 눈치채기 쉬워집니다

예상 출력: 파일 저장이라 출력이 없습니다.

7. 트러블슈팅

설명
증상원인해결
Failed with non-blocking status code: 알림이 뜬다 스크립트 경로가 없거나 실행 권한이 없음 경로와 chmod +x를 확인합니다. 이 알림이 뜨는 동안 게이트는 꺼져 있습니다(4-5 ②).
/hooks에 훅이 안 보인다 JSON 오류로 설정 파일 전체가 무시됨 중급 02에서 배운 대로 python3 -m json.tool로 검증하고 claude doctor로 거부된 항목을 봅니다.
막아야 할 것이 통과한다 매처가 안 맞거나 경로 판정이 좁음. 또는 매처에 없는 도구(예: Bash)로 우회했을 수 있습니다(4-2) 예제 코드 ②로 단독 검증합니다. 특히 Windows 경로와 상대 경로 케이스를 확인하세요. Bash로도 같은 파일을 고칠 수 있다면 매처에 Bash를 추가하고 스크립트를 확장하세요.
정당한 작업까지 막힌다 매처가 너무 넓거나 endswith 판정이 과함 예제 코드 ②의 "비슷한 이름" 케이스가 통과하는지 봅니다. Edit.*처럼 앵커 없는 정규식을 썼다면 정확 일치로 바꾸세요(4-4).
훅을 잠시 끄고 싶다 정당한 이유로 보호 대상을 고쳐야 함 이번 실행만 끄려면 claude --settings '{"disableAllHooks": true}'를 씁니다. 프로젝트·로컬 설정보다 우선합니다. 작업이 끝나면 반드시 원래대로 돌아오세요. 관리 설정(정책) 훅은 이 방법으로 꺼지지 않습니다 — 관리 설정 자체에서 꺼야 합니다. (출처: code.claude.com/docs/en/hooks-guide, 2026-08-26 확인)

7-2. 흔한 잘못된 습관

습관겉으로 나타나는 모습대응
훅을 걸고 검증하지 않는다 지켜 준다고 믿고 경계를 늦춤. 실제로는 처음부터 꺼져 있었음 등록 전 단독 검증(4단계)과 등록 후 실동작 확인(7·8단계)을 한 세트로 굳힙니다.
차단만 확인하고 통과는 확인 안 한다 안전해 보임. 정당한 작업이 막혀 팀이 훅을 통째로 끄게 됨 막아야 할 것과 통과시켜야 할 것을 둘 다 시험합니다(8단계).
확인되지 않은 규칙을 훅으로 만든다 꼼꼼해 보임. 실제로는 [GUESS]를 강제해 정당한 작업을 막음 [FACT]만 훅 대상으로 삼습니다(1단계). 나머지는 리뷰 스킬(중급 04)로 지적만 하게 둡니다.
팀에 알리지 않고 커밋한다 내 환경은 잘 돌아감. 팀원이 이유 모를 차단을 만나 시간을 버림 프로젝트 설정 훅은 남의 작업을 막는 규칙입니다. 거부 사유에 근거 문서를 적고(예제 ①의 REASON), 커밋 전에 알립니다.
훅 하나로 모든 것을 막으려 한다 정규식이 점점 길어지고 아무도 못 고치는 스크립트가 됨 정적으로 표현 가능한 것은 permissions.deny로 옮깁니다(4-6). 훅은 판단이 필요한 것만 맡습니다.

CLI로 직접 실행해 검증한 것(v2.1.246): 훅 스크립트·검증 스크립트·설정 파일을 7가지 입력 케이스로 직접 실행, 실제 Claude Code 세션에서 보호 대상 파일 수정이 차단되는지(프롬프트 A)와 다른 파일 수정은 통과하는지(프롬프트 B), --dangerously-skip-permissions로도 차단이 유지되는지, 스크립트 경로 오타 시 게이트가 조용히 열리고 복구 후 다시 차단되는지, claude doctor가 잘못된 훅 설정을 실제로 잡아내는지를 재현했습니다.

이번에 새로 찾아 반영한 것: "matcher": "Edit|Write"는 같은 파일을 Bash로 고치는 경로를 막지 못합니다. 공식 가이드의 경고를 CLI로 재현해 확인했고 4-2에 콜아웃으로 추가했습니다. 아울러 본문 두 곳에서 공식 문서의 뜻을 따옴표로 감싸 인용문처럼 적었던 부분(exit 0의 의미, "첫 실행에서 지켜보라"는 권고)을 원문에 없는 직접 인용이었음을 확인하고 일반 서술로 고쳤습니다.
