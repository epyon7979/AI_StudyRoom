2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. 번들 스킬 /code-review를 실행하고 그 결과의 한계를 짚을 수 있다.
  2. 프로젝트 고유 규칙을 담은 리뷰 스킬을 만들어 번들 리뷰가 못 잡는 문제를 잡을 수 있다.
  3. 리뷰에서 나온 지적을 고치고, 동작을 확인한 뒤 커밋할 수 있다.

3. 사전 준비

설명

항목내용

3-2. 이 문서의 표기 방식

3-3. 이름을 code-review로 짓지 않습니다

번들 스킬을 덮어쓰지 않도록

프로젝트의 .claude/skills/에 code-review라는 스킬을 만들면 번들 /code-review를 대체합니다. 다만 번들의 별칭인 /review는 대체되지 않아 계속 번들 쪽이 실행됩니다. 그러면 이 모듈의 목적인 "둘을 비교하기"가 불가능해집니다. 그래서 이 모듈의 스킬 이름은 legacy-review입니다. (출처: code.claude.com/docs/en/skills, 2026-08-26 확인 / CLI 실행 결과 직접 확인 — 동일 이름의 프로젝트 스킬을 만들어 /code-review가 대체되는 것을 재현)

실무에서도 마찬가지입니다. 번들 스킬과 같은 이름을 쓰기 전에 대체할 의도가 맞는지 먼저 확인하세요.

4. 핵심 개념

설명

4-1. 결론부터

일반적인 코드 리뷰는 이미 제공됩니다. 우리가 만들어야 할 것은 "이 프로젝트에서만 문제가 되는 것"을 잡는 리뷰입니다. 하드코딩·예외 무시 같은 일반 문제는 번들 리뷰가 잡습니다. 하지만 "이 출력 형식을 바꾸면 다른 시스템이 깨진다"는 코드 어디에도 안 적혀 있습니다.

4-2. 번들 스킬이 이미 있습니다

Claude Code에는 /doctor, /code-review, /batch, /debug, /loop 같은 번들 스킬이 포함돼 있습니다. 번들 스킬은 프롬프트 기반이라, Claude에게 상세한 지시를 주고 도구로 작업을 조율하게 합니다. 호출 방법은 다른 스킬과 같이 / 뒤에 이름을 입력하는 것입니다. (출처: code.claude.com/docs/en/skills, 2026-08-26 확인 / CLI 실행 결과 직접 확인 — 다섯 스킬 모두 별도 설치 없이 세션 커맨드 목록에 나타남)

만들기 전에 있는지 먼저 확인하세요

중급 03에서 스킬 만드는 법을 배웠다고 전부 새로 만들 필요는 없습니다. /를 입력해 목록을 훑어보면 이미 있는 것을 다시 만드는 낭비를 피할 수 있습니다.

/code-review는 "지금까지의 코드 전체"가 아니라 diff를 봅니다

/code-review의 실제 설명은 "현재 diff, 또는 지정한 PR 번호·브랜치·경로를 검토"하는 도구입니다. 커밋할 변경 사항이 없는 깨끗한 작업 트리에서 범위를 지정하지 않고 실행하면, 업스트림 브랜치가 없는 한 git diff HEAD~1..HEAD(가장 최근 커밋 하나)만 봅니다 — 지금 이 샌드박스처럼 그 커밋이 문서 수정뿐이면 지적 사항이 0개로 끝납니다. 그래서 5단계에서는 범위를 직접 지정합니다. (CLI 실행 결과 직접 확인 — Claude Code v2.1.246, 2026-08-26)

4-3. 번들 리뷰가 모르는 것

구분예 (이 샌드박스)번들 리뷰가 잡는가
일반적인 코드 문제except Exception: pass로 예외를 삼킴대체로 잡음
일반적인 코드 문제URL이 코드에 하드코딩됨대체로 잡음
이 프로젝트만의 규칙출력 문구 형식을 바꾸면 안 됨 (다른 시스템이 파싱)못 잡음 — 코드에 근거가 없음
이 프로젝트만의 규칙daily_batch.sh가 실제 운영 진입점못 잡음 — 문서에 없음

아래 두 줄이 바로 중급 01의 정찰로 알아낸 것입니다. 그때 docs/HANDOVER.md에 남겨 뒀기 때문에 지금 리뷰 기준으로 쓸 수 있습니다. 정찰 결과를 파일로 남기라고 했던 이유가 여기서 드러납니다.

4-4. 리뷰 스킬은 내가 부를 때만 돌게 합니다

리뷰는 여러 파일을 읽어 사용량을 많이 씁니다. Claude가 판단해서 아무 때나 돌리면 곤란하므로 disable-model-invocation: true를 붙입니다. 중급 03의 4-5에서 배운 기준 그대로입니다.

4-5. 리뷰 지적을 고칠 때의 순서

순서할 일왜
1지적을 고칠 것과 안 고칠 것으로 나눈다리뷰 지적이 전부 옳지는 않습니다. 의도된 설계일 수도 있습니다
2한 번에 하나만 고친다여러 개를 한꺼번에 고치면 무엇이 무엇을 깨뜨렸는지 알 수 없습니다
3/check-app으로 동작을 확인한다중급 03에서 만든 스킬을 여기서 씁니다
4커밋한다다음 수정의 복구 지점이 됩니다
리뷰가 지적했다고 다 고치는 것이 아닙니다

이 샌드박스의 DRY_RUN = True는 리뷰가 "미구현"이라고 지적할 수 있지만, 실습 환경에서 외부 요청을 막으려고 일부러 그렇게 둔 것입니다. 실무에서도 마찬가지로 "왜 이렇게 돼 있는지" 모르는 코드는 고치기 전에 확인해야 합니다. 그 확인 목록이 중급 01에서 만든 질문 목록입니다.

5. 단계별 실습

실습

만들 결과물: 프로젝트 리뷰 스킬로 찾아낸 문제 1건을 고쳐 커밋한 git 히스토리.

  1. 시작 상태를 확인합니다
    셸 명령 · 예상 출력
    $ cd ~/claude-code-sandbox
$ ls docs/HANDOVER.md .claude/skills/check-app/SKILL.md
docs/HANDOVER.md
.claude/skills/check-app/SKILL.md

$ git status
On branch master
nothing to commit, working tree clean

    브랜치 이름은 main일 수도, master일 수도 있습니다 — init.defaultBranch를 설정하지 않은 환경(이 커리큘럼의 실습 환경 포함)에서는 master로 나옵니다(중급 01 참고). 어느 쪽이든 nothing to commit, working tree clean이면 정상입니다.

    두 파일이 없으면 중급 01 또는 03을 먼저 마치세요.

  2. 번들 리뷰를 먼저 돌립니다

    세션을 열고 아래를 입력합니다. 아직 아무것도 만들지 않은 상태에서 기본 제공 리뷰가 무엇을 잡는지 봅니다. /code-review는 diff를 보는 도구입니다(4-2) — 지금 작업 트리는 깨끗하므로 범위를 지정하지 않으면 볼 것이 없습니다. 아래 값은 git의 "빈 트리(empty tree)" 객체를 가리키는 고정 해시로, 모든 저장소에서 동일합니다. 이 값과 비교하면 지금까지 커밋이 몇 개 쌓였는지와 무관하게 현재 코드 전체를 diff로 보여줍니다.

    세션 입력
    /code-review 4b825dc642cb6eb9a060e54bf8d69288fbee4904

    해시가 길어 보여도 그대로 입력하면 됩니다. 오타가 나면 git이 "존재하지 않는 개체"로 오류를 냅니다. (CLI 실행 결과 직접 확인 — Claude Code v2.1.246, 2026-08-26)

    결과를 메모해 두세요. 6단계에서 비교합니다.

  3. 번들 리뷰가 못 잡은 것을 확인합니다

    리뷰 결과에 아래 두 가지가 없는지 확인합니다.

    • 출력 문구 형식을 바꾸면 안 된다는 지적
    • scripts/daily_batch.sh가 운영 진입점이라는 언급

    없는 것이 정상입니다. 코드에 근거가 없으니 알 수 없습니다. 이것이 4-3에서 말한 한계입니다.

    여기까지 — 번들 리뷰의 한계 확인
    • /code-review를 실행해 결과를 받았다
    • 일반적인 코드 문제는 잡혔다
    • 프로젝트 고유 규칙은 안 잡혔다는 것을 확인했다

    고유 규칙까지 잡혔다면 CLAUDE.md에 이미 적혀 있어서일 수 있습니다. 그래도 다음 단계는 그대로 진행하세요 — 리뷰 기준을 명시적으로 만드는 것이 목적입니다.

  4. 리뷰 기준을 HANDOVER.md에서 가져옵니다

    중급 01에서 만든 문서를 다시 엽니다. [FACT]로 확인된 항목이 리뷰 기준이 됩니다.

    셸 명령
    cat docs/HANDOVER.md

    [WEAK]·[GUESS] 항목은 리뷰 기준으로 쓰지 않습니다. 확인되지 않은 것을 기준 삼으면 리뷰가 틀린 지적을 하게 됩니다.

  5. 리뷰 스킬을 만듭니다
    셸 명령
    mkdir -p .claude/skills/legacy-review

    6번 절의 SKILL.md 전문을 .claude/skills/legacy-review/SKILL.md에 저장합니다.

  6. 프로젝트 리뷰를 돌립니다 (프롬프트 A)
    세션 입력
    /legacy-review

    2단계 결과와 비교하세요. 같은 코드인데 지적 내용이 달라야 합니다.

    [캡처 C-01]
    화면
    /legacy-review 실행 결과
    진입 경로
    SKILL.md 저장 후 세션에서 /legacy-review
    캡처 범위
    프로젝트 고유 규칙 관련 지적이 보이는 범위
    강조 표시
    출력 형식 또는 운영 진입점 관련 지적(빨간 테두리)
    캡션
    번들 리뷰가 못 잡는 프로젝트 고유 규칙을 리뷰 기준으로 넣은 결과.
    화면 캡처 대신 실제 실행 결과

    이 자리는 원래 화면 캡처 대상이었지만, /legacy-review의 응답은 메뉴·선택지 없는 일반 텍스트라 캡처와 내용이 같습니다. 그래서 같은 절차로 재구성한 샌드박스에서 SKILL.md 저장 후 claude -p "/legacy-review"를 실제 실행해 받은 응답 전문(생략 없음)을 그대로 옮겼습니다(2026-08-27, Claude Code v2.1.247). 비교 기준으로 쓴 번들 /code-review 4b825dc642cb6eb9a060e54bf8d69288fbee4904도 같은 세션에서 먼저 실제 실행했고, 그 결과 6건에는 출력 형식·daily_batch.sh 운영 진입점 언급이 정말로 없다는 2단계의 전제를 직접 확인했습니다. 지적 내용과 문구는 실행마다 달라질 수 있는 응답 예시입니다.

    셸 명령 · 실제 출력 (claude -p "/legacy-review")
    $ claude -p "/legacy-review"
변경 내역을 확인했습니다(`.claude/skills/legacy-review/` 스킬 디렉터리 추가 외 코드 변경 없음). 아래는 저장소 전체(특히 `app.py`, `utils/formatter.py`, `utils/notify.py`, `utils/legacy_export.py`, `scripts/daily_batch.sh`, `config/settings.ini`)를 규칙 기준으로 검토한 결과입니다.

### 규칙 위반

없음.

- `utils/formatter.py:2`의 `build_alert` 출력 형식은 `"[재고 부족] {item['name']} - 현재 {item['quantity']}개"`로 원래 형식과 동일하게 유지되어 있음.
- `scripts/daily_batch.sh`를 실제 운영 진입점으로 포함해 검토함(app.py만 보고 판단하지 않음).
- `utils/notify.py:5`의 `DRY_RUN = True`는 규칙에 따라 미구현으로 지적하지 않음.

### 일반적인 문제

1. **`app.py:18`** — `threshold = int(sys.argv[2]) if len(sys.argv) > 2 else THRESHOLD`: 두 번째 인자가 숫자가 아니면 예외 처리 없이 `ValueError`로 크래시.
2. **`app.py:20`** — `low = [i for i in items if int(i["quantity"]) < threshold]`: `quantity` 값이 숫자가 아니거나 컬럼이 없는 CSV 행이면 예외 처리 없이 크래시.
3. **`scripts/daily_batch.sh:4`** — `python3 app.py inventory.csv > /tmp/alerts.txt 2>&1`: stdout·stderr를 함께 `/tmp/alerts.txt`에 기록하고, 종료 코드 확인 없이 곧바로 5번째 줄에서 `legacy_export`를 실행. `app.py`가 (1·2번 문제로) 크래시하면 트레이스백이 alerts.txt에 섞여 들어가고, 이 파일이 그대로 `legacy_export.py`의 입력이 됨.
4. **`utils/legacy_export.py:17-20`**
   ```python
   try:
       send(len(lines))
   except Exception:
       pass
   ```
   `send()` 실패를 로그 없이 완전히 삼킴. 알림 실패 여부를 추적할 방법이 없음.
5. **`utils/legacy_export.py:12`** — `with open(path, encoding="utf-8") as f:`: `path`(예: `/tmp/alerts.txt`)가 없을 때 예외 처리 없이 `FileNotFoundError`로 크래시.
6. **`utils/notify.py:4`** — `WEBHOOK_URL = "https://ops-internal.example.corp/hooks/inventory"`: 하드코딩. `config/settings.ini`에 `[notify]` 섹션이 있는데도 URL은 분리되어 있지 않음.
7. **`utils/legacy_export.py:6`** — `OUT_DIR = "/tmp/inventory_out"`: 하드코딩.
8. **`config/settings.ini:3`** — `timeout = 45`: `utils/notify.py`는 `retry`만 `_cfg.getint`로 읽고(`utils/notify.py:12`) `timeout`은 코드 어디에서도 참조하지 않음. 사용되지 않는 설정값.
9. **`config/settings.ini:6`** — `keep_days = 90`: `utils/legacy_export.py`에 파일 정리(retention) 로직 자체가 없어 이 값을 참조하는 곳이 없음. 사용되지 않는 설정값.

### 판단 보류

- **`scripts/daily_batch.sh:2`** 주석 "운영 크론에서 매일 07:00 실행"이 지금도 유효한지 — crontab 등록 여부는 저장소 안에서 확인 불가.
- **`config/settings.ini`의 `timeout`(3행)·`keep_days`(6행)** — 향후 구현 예정 자리표시자인지, 이미 쓰이지 않는 죽은 설정인지 코드만으로는 판단 불가.
- **`utils/legacy_export.py`** 파일명의 "legacy"가 가리키는 이전 시스템/프로세스가 무엇인지 — 이름 외 근거(커밋 이력, 문서)가 저장소에 없음.

    굵게 강조한 두 줄이 이 모듈의 요점입니다 — 번들 /code-review는 몰랐던 출력 형식 유지와 daily_batch.sh 운영 진입점을 이번에는 리뷰 기준에 넣어 명시적으로 확인했습니다.
