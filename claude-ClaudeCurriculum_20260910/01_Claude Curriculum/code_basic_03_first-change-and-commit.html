2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. 자연어로 코드 변경을 요청하고, 제시된 변경 내용을 검토해 승인할 수 있다.
  2. 대화로 변경 내역을 확인하고 커밋할 수 있다.
  3. 세션을 종료했다가 이어가거나, 맥락을 정리해 새로 시작할 수 있다.

모듈 01·02와 같습니다. 커맨드·플래그·화면 문구는 영문 원문 그대로 싣고 설명만 한국어로 씁니다.

  • 시작 전 복구 지점을 확인합니다. 모듈 02의 안전장치 ①입니다. 무엇이 잘못돼도 되돌릴 수 있습니다.
  • 샌드박스에서만 합니다. 사내 실제 저장소에서는 하지 않습니다.

4. 핵심 개념

설명

4-1. 결론부터

Claude가 코드를 고칠 때 내가 할 일은 "변경 내용을 읽고 승인할지 정하는 것"입니다. 승인 화면을 대충 넘기면 Claude Code를 쓰는 의미가 절반으로 줄어듭니다. 이 모듈의 핵심은 빠르게 고치는 법이 아니라 고쳐진 것을 확인하는 법입니다.

4-2. 승인 화면에서 고를 수 있는 것

Manual 모드에서 Claude가 파일을 고치거나 명령을 실행하려 하면 변경 내용과 함께 승인 여부를 묻습니다. 선택지 중 "Yes, and don't ask again"은 주의가 필요합니다.

초급에서는 "Yes, and don't ask again"을 고르지 마세요

이 선택지는 단순한 한 번의 승인이 아니고, 무엇을 승인하느냐에 따라 지속 범위가 다릅니다. 파일 수정 승인에서 고르면 설정 파일에 저장되지는 않지만 이번 세션이 끝날 때까지 앞으로의 파일 수정 승인을 전부 건너뜁니다. Bash 명령이나 WebFetch 도메인처럼 영구 저장되는 경우에는 그 규칙이 git 저장소 루트의 .claude/settings.local.json 파일에 기록되어 다음 세션에도 남습니다. (출처: code.claude.com/docs/en/permissions, 2026-08-26 확인)

초급 트랙은 설정을 바꾸지 않는 것이 원칙이고, 무엇보다 "앞으로 묻지 마라"를 무엇에 대해 허용했는지 기억하지 못한 채 쌓이는 것이 위험합니다. 이 모듈에서는 매번 개별 승인만 합니다. 권한 규칙을 의도적으로 설계하는 방법은 중급에서 다룹니다.

4-3. 무슨 명령인지 모르겠으면 Ctrl+E

Bash나 PowerShell 명령에 대한 승인 프롬프트에서 Ctrl+E를 누르면 그 명령이 무엇을 하는지, Claude가 왜 실행하려는지, 무엇이 잘못될 수 있는지 설명이 나옵니다. 설명에는 Low risk, Med risk, High risk 중 하나로 위험도가 표시됩니다. (출처: code.claude.com/docs/en/permissions, 2026-08-26 확인)

눌러도 안전합니다

설명을 표시한다고 명령이 실행되지는 않습니다. 설명은 Ctrl+E를 누를 때만 생성되고, 다시 누르면 숨겨집니다. 모르는 명령이 나오면 승인 전에 눌러 보는 습관을 들이세요. 초급 학습자에게 가장 실용적인 안전장치입니다. (출처: code.claude.com/docs/en/permissions, 2026-08-26 확인)

4-4. Claude의 "다 됐습니다"를 그대로 믿지 않습니다

Claude가 변경을 마쳤다고 해도, 내가 직접 실행해 보기 전까지는 확인된 것이 아닙니다. 이 모듈의 실습은 변경 후 반드시 두 가지를 합니다.

확인방법무엇을 잡는가
기존 동작이 그대로인가인자 없이 실행해 예전과 같은 결과가 나오는지고치다가 원래 되던 게 깨진 경우
새 동작이 되는가새로 추가된 방식으로 실행요청한 것이 실제로 반영되지 않은 경우

4-5. 세션을 이어가는 세 가지 방법

명령구분하는 일
claude -c셸현재 디렉터리의 가장 최근 대화를 이어서 시작
claude -r셸이전 대화 중 하나를 골라서 이어서 시작
/clear세션현재 세션의 대화 기록을 비움 (세션은 유지)

앞의 둘은 맥락을 가져오는 것이고 /clear는 맥락을 버리는 것입니다. 한 작업을 마치고 성격이 다른 다음 작업으로 넘어갈 때 /clear를 쓰면, 앞 작업의 내용이 새 작업에 끼어드는 것을 막을 수 있습니다. (출처: code.claude.com/docs/en/quickstart, 2026-08-26 확인)

5. 단계별 실습

실습

만들 결과물: Claude가 만든 변경이 커밋된 git 히스토리 1건.

  1. 샌드박스로 이동해 복구 지점을 확인합니다
    셸 명령 · 예상 출력
    $ cd ~/claude-code-sandbox
$ git status
On branch main
nothing to commit, working tree clean

    브랜치 이름은 git 설정(init.defaultBranch)에 따라 main 대신 master로 보일 수 있습니다. 기본 설정을 바꾸지 않은 환경에서는 master로 나옵니다. 어느 쪽이든 nothing to commit, working tree clean이면 정상입니다. (CLI 실행 결과 직접 확인, 2026-08-26)

    깨끗하지 않다면 먼저 커밋하거나 되돌린 뒤 진행하세요. 이 상태가 오늘의 복구 지점입니다.

사실 확인 기준

승인 선택지의 저장 위치와 Ctrl+E 설명 기능은 권한 설정 공식 문서로 확인했습니다. 이번 확인에서 문서 원문의 표를 다시 대조한 결과 파일 수정 승인은 세션 종료까지만 유지되고 설정 파일에는 저장되지 않으며, Bash·WebFetch 승인만 .claude/settings.local.json에 영구 저장된다는 차이를 발견해 4-2와 5단계의 설명을 그에 맞게 고쳤습니다. 셸 명령(claude -c, claude -r)과 세션 커맨드(/clear)는 Quickstart로 확인했습니다.

실습 흐름은 위 CLI·git 실행 결과로 처음부터 끝까지 직접 재현했습니다. 그 과정에서 git init 직후 브랜치 이름은 init.defaultBranch를 설정하지 않은 환경에서 main이 아니라 master로 생성됨을 확인해 1·9단계 예시에 안내를 추가했습니다. 모듈 01에서 추가한 .gitignore(__pycache__/ 제외) 덕분에 이 모듈에서 python3 app.py를 실행해도 git status가 계속 깨끗하게 유지되는 것도 함께 확인했습니다. 코드 구현 방식(sys.argv 등)은 실행마다 다를 수 있으므로 성공 확인 기준은 코드가 아닌 실행 결과로 잡았습니다.

2026-08-27에는 C-01~C-03의 화면 목업을 만들면서 같은 샌드박스를 다시 재현해 claude -p 비대화 모드로 프롬프트 A·B를 실행하고 git diff로 실제 변경분을 확인했습니다(v2.1.247). C-01의 diff와 C-03의 claude -p -c 응답(커밋 해시 포함)은 이때 실제로 받은 결과를 옮긴 것입니다. 승인 화면·Ctrl+E 설명·이어진 세션 화면은 로그인을 마친 대화형 세션에서만 나타나는데, 이 클라우드 환경에는 연결된 브라우저가 없어 세 캡처 모두 근사 목업으로 대체했습니다.
