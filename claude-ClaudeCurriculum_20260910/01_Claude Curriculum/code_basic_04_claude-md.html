2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. CLAUDE.md가 하는 일과 어디에 두어야 하는지 설명할 수 있다.
  2. /init으로 초안을 만들고 프로젝트에 맞게 다듬을 수 있다.
  3. /context로 파일이 실제로 로드됐는지 확인할 수 있다.

4. 핵심 개념

설명

4-1. 결론부터

Claude Code는 세션이 시작될 때마다 빈 상태로 출발합니다. 어제 알려 준 것을 오늘은 모릅니다. CLAUDE.md는 매번 다시 설명하지 않기 위해 적어 두는 파일이고, Claude가 세션을 시작할 때마다 읽습니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

4-2. 기억하는 방법은 두 가지입니다

CLAUDE.md 파일자동 메모리 (auto memory)
누가 쓰는가내가Claude가
무엇이 담기는가지시와 규칙학습된 것과 패턴
범위프로젝트, 사용자, 조직저장소 단위
언제 로드되는가모든 세션모든 세션 (첫 200줄 또는 25KB)
쓰임새코딩 표준, 워크플로, 프로젝트 구조내 선호, 내가 준 수정 지시, 코드만 봐서는 알 수 없는 프로젝트 맥락

둘 다 대화 시작 시 함께 로드됩니다. Claude의 행동을 내가 정하고 싶으면 CLAUDE.md를 쓰고, 내 수정 사항을 Claude가 알아서 배우게 하려면 자동 메모리에 맡깁니다. 자동 메모리는 기본으로 켜져 있습니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

4-3. 어디에 두는가

범위가 넓은 것부터 좁은 것 순으로 로드됩니다.

범위위치공유 대상
관리 정책OS별 시스템 경로 (IT·DevOps가 배포)조직 내 모든 사용자
사용자~/.claude/CLAUDE.md나 혼자 (모든 프로젝트)
프로젝트./CLAUDE.md 또는 ./.claude/CLAUDE.md버전 관리로 팀 전체
로컬./CLAUDE.local.md나 혼자 (현재 프로젝트). .gitignore에 추가 필요

이 모듈에서는 프로젝트 범위만 다룹니다. 팀과 공유되는 자리라 실무에서 가장 많이 쓰기 때문입니다. 나머지 세 범위는 중급·상급에서 다룹니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

4-4. 무엇을 어떻게 적는가

공식 문서는 "다시 설명하게 될 것을 적어 두는 자리"로 설명하며, 아래 네 가지 신호가 오면 CLAUDE.md에 추가하라고 안내합니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

  • Claude가 같은 실수를 두 번째 한다
  • 코드 리뷰에서 Claude가 알았어야 할 것이 지적된다
  • 지난 세션에 입력했던 같은 수정 지시를 또 입력한다
  • 새 팀원이 생산적으로 일하려면 같은 맥락이 필요하다

쓰는 방식은 세 가지가 핵심입니다.

원칙내용예
분량파일당 200줄 이하를 목표로. 길수록 컨텍스트를 많이 먹고 준수도가 떨어집니다—
구조마크다운 제목과 목록으로 묶습니다—
구체성검증 가능할 만큼 구체적으로"코드를 잘 포맷하라" ✕ → "들여쓰기는 공백 2칸" ○
"변경을 테스트하라" ✕ → "커밋 전에 npm test 실행" ○
서로 모순되는 규칙을 적지 마세요

두 규칙이 충돌하면 Claude가 그중 하나를 임의로 고를 수 있습니다. 주기적으로 읽어 보며 낡거나 모순된 지시를 지우세요. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

4-5. 강제가 아니라 컨텍스트입니다

가장 중요한 한계

CLAUDE.md의 내용은 시스템 프롬프트가 아니라 시스템 프롬프트 뒤에 오는 사용자 메시지로 전달됩니다. Claude는 이를 읽고 따르려 하지만 엄격한 준수가 보장되지는 않습니다. 특히 모호하거나 서로 충돌하는 지시일수록 그렇습니다. (출처: code.claude.com/docs/en/memory, 2026-08-26 확인)

즉 "CLAUDE.md에 적었으니 안전하다"고 생각하면 안 됩니다. 무슨 일이 있어도 반드시 막아야 하는 동작이라면 CLAUDE.md가 아니라 훅(Hooks)으로 처리해야 하며, 그건 상급 트랙에서 다룹니다. 모듈 02·03에서 배운 권한 모드와 git 복구 지점은 여전히 필요합니다.

## 이 프로젝트의 규칙
- utils/formatter.py의 출력 문구 형식은 바꾸지 않는다. 다른 시스템이 이 형식을 파싱한다.

- 커밋은 사용자가 요청할 때만 한다.

CLAUDE.md의 네 가지 범위와 로드 순서, /init·/memory의 동작, 200줄 기준과 구체성 원칙, 자동 메모리의 기본 활성 상태, 그리고 "시스템 프롬프트가 아니라 사용자 메시지로 전달되어 엄격한 준수가 보장되지 않는다"는 한계를 모두 공식 메모리 문서로 다시 대조했습니다. /context의 Memory Files 표시(생성 전 비어 있음 → 생성 직후 즉시 표시, User·Project·Local 동시 표시)와 CLAUDE.md에 적은 규칙이 실제로 응답에 반영되는지는 위 CLI 실행으로 직접 재현했습니다. 이번 대조에서 자동 메모리의 "쓰임새" 설명이 공식 문서와 달랐던 것(기존: "빌드 명령, 디버깅 통찰, Claude가 알아낸 선호" → 문서상 실제로는 "내 선호, 내가 준 수정 사항, 코드에서 유추할 수 없는 프로젝트 맥락"이며 "빌드 명령"은 오히려 CLAUDE.md 쪽 설명입니다)을 발견해 4-2 표를 고쳤고, git init 직후 브랜치 이름이 init.defaultBranch 미설정 환경에서 main이 아니라 master로 생성됨을 확인해 1·12단계 예시에 안내를 추가했습니다(모듈 01·03과 동일한 방식). 9절의 C-02 캡처 안내도 "7단계 이후"라는 인과관계가 부정확해 "4단계(/init)에서 파일이 생기는 즉시"로 바로잡았습니다. 초급 범위를 넘는 항목(.claude/rules/, 경로별 규칙, @path 임포트, 조직 배포용 관리 정책, claudeMdExcludes)은 같은 문서에서 확인했으나 다루지 않았습니다.

2026-08-27에는 C-01~C-03의 화면 목업을 만들면서 같은 확인을 반복해 위 두 제약(/init 비활성화, /memory 비대화 모드 미지원)이 오늘도 그대로임을 재확인했습니다. 공식 Slash commands 문서에서 /context가 실제로는 "색으로 구분된 그리드(colored grid)"로 시각화된다는 것을 추가로 확인해, C-02 목업에 그 배치가 실제 화면과 다를 수 있다는 점을 명시했습니다. C-01의 CLAUDE.md 내용과 C-02의 Memory files 표시는 이때 실제로 생성·확인한 결과를 옮긴 것입니다. 대화형 승인 화면·/context 그리드·/memory 목록 UI 자체는 로그인을 마쳐야 나타나는데, 이 클라우드 환경에는 연결된 브라우저가 없어 세 캡처 모두 근사 목업으로 대체했습니다.
