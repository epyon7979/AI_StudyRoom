2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. 무인 실행에서 컨텍스트가 어떻게 달라지는지 설명하고 --bare 여부를 판단할 수 있다.
  2. 결정론적 검사와 비결정론적 판단을 나눠 자동화할 수 있다.
  3. 팀·조직 배포의 위험을 평가해 배포 계획서로 남길 수 있다.

3-3. 이 모듈에서 실습하지 않는 것

개인 구독 기준이라 조직 배포는 계획서로 대신합니다

조직 관리 설정 배포는 Owner 권한이 필요해 대부분의 학습자가 실습할 수 없습니다. 이 커리큘럼은 실제 배포 대신 배포 계획서와 위험 평가를 결과물로 삼습니다. §3-3이 정의한 상급의 "설계 판단과 트레이드오프 중심"에 부합하며, 권한을 가진 사람에게 그대로 제출할 수 있는 문서가 나옵니다.

실제 CI 시스템에 붙이는 것도 제품·환경마다 달라 실습에 넣지 않았습니다. 대신 CI가 하는 일(명령 실행 → 종료 코드로 분기)을 로컬에서 그대로 재현합니다. GitHub Actions는 예외적으로 공식 액션(anthropics/claude-code-action)이 있어 설정이 정형화돼 있지만, 이 모듈은 특정 CI 제품에 매이지 않는 원리(4-2~4-4)를 먼저 다지는 것이 목표라 이번에도 실습에는 넣지 않았습니다. 실제 연동은 참고 자료의 공식 문서를 따라 하세요.

4. 핵심 개념

설명

4-1. 결론부터

무인 실행의 진짜 위험은 Claude가 실수하는 것이 아니라, 실수를 잡아 줄 사람이 없다는 것입니다. 대화형에서는 승인 화면이 마지막 방어선이었습니다. 무인 실행에는 그 화면이 없습니다. 그래서 지금까지 쌓은 안전망이 그 자리에서도 도는지가 전부입니다.

4-2. 무인 실행의 기본

-p(또는 --print)를 붙이면 대화형 화면 없이 프롬프트를 한 번 처리하고 종료합니다. Claude Code는 성공하면 종료 코드 0, 실행이 실패하면 0이 아닌 코드로 끝나므로 스크립트가 종료 상태로 분기할 수 있습니다. (출처: code.claude.com/docs/en/headless, 2026-08-26 확인)

실패 유형어디로 나오는가
잘못된 플래그를 넘김실행이 시작되기 전에 stderr로 보고
실행 중 실패 (예: 인증 누락)실패가 결과로서 stdout에 출력

둘의 출력 위치가 다르다는 점이 중요합니다. stdout만 보고 성공을 판정하면 인증 실패를 "결과"로 오인할 수 있습니다. 종료 코드를 함께 봐야 합니다.

4-3. --bare가 이 모듈의 핵심입니다

우리가 만든 안전망 대부분이 여기서 사라집니다

--bare는 훅, 스킬, 커스텀 커맨드, 서브에이전트, 플러그인, MCP 서버, 자동 메모리, CLAUDE.md의 자동 탐색을 건너뛰어 시작 시간을 줄입니다. 붙이지 않으면 claude -p는 대화형 세션과 똑같은 컨텍스트를 로드합니다 — 작업 디렉터리나 ~/.claude에 설정된 모든 것을 포함해서요. (출처: code.claude.com/docs/en/headless, 2026-08-26 확인)

이 커리큘럼에서 만든 것과 대조하면 이렇습니다.

--bare가 건너뛰는 것우리가 만든 곳
훅상급 01·02·04 — 차단·안전망·점검
스킬중급 03·04 — check-app·legacy-review
서브에이전트상급 03 — recon
CLAUDE.md초급 04 — 프로젝트 규칙
MCP 서버중급 05

다섯 개가 동작하지 않습니다. 그런데 공식 문서는 --bare를 권하는 이유도 함께 밝힙니다 — CI와 스크립트에서 모든 기기에서 같은 결과가 필요할 때 유용하며, 팀원의 ~/.claude에 있는 훅이나 프로젝트 .mcp.json의 MCP 서버가 돌지 않습니다. 바로 그것들을 읽지 않기 때문입니다. (출처: code.claude.com/docs/en/headless, 2026-08-26 확인)

--bare 없이--bare로
우리 안전망동작함안 동작함
재현성기기마다 달라질 수 있음모든 기기에서 동일
남의 개인 설정딸려 들어옴차단됨
시작 시간느림빠름
둘 다 좋은 선택이 아닙니다 — 그래서 나눕니다

안전망을 쓰려고 --bare를 빼면 팀원의 개인 설정까지 CI에 딸려 들어옵니다. 재현성을 지키려고 붙이면 안전망이 통째로 빠집니다.

해결은 Claude에게 안전을 맡기지 않는 것입니다(4-4).

4-4. 결정론적인 것과 비결정론적인 것을 나눕니다

이것이 이 모듈의 설계 판단입니다.

결정론적 검사비결정론적 판단
예상급 04의 점검 스크립트, 상급 02의 특성화 테스트claude -p로 받는 리뷰·요약
같은 입력에 같은 결과예아니오
Claude가 필요한가아니오예
CI에서의 역할빌드를 중단시킴조언만. 중단시키지 않음
모델 응답으로 빌드를 막지 마세요

초급 04부터 반복한 원칙입니다 — 응답은 실행마다 달라집니다. 같은 코드에 오늘은 통과하고 내일은 실패하는 게이트는 팀이 결국 꺼 버립니다. 그리고 한 번 꺼진 게이트는 다시 켜지지 않습니다.

비결정론적 판단은 사람이 읽을 조언으로만 남기세요. 막아야 할 것은 결정론적 검사로 표현할 수 있을 때만 막습니다.

4-5. 무인 실행에서 프롬프트가 달라져야 합니다

대화형 프롬프트를 그대로 쓰면 안 됩니다. 되물을 사람이 없기 때문입니다.

대화형에서는 괜찮은 것무인 실행에서 생기는 문제
"필요하면 알려 주세요"로 끝나는 프롬프트답할 사람이 없어 일이 중간에 멈춤
맥락을 대화로 보충보충할 턴이 없음 — 프롬프트에 다 넣어야 함
승인 화면에서 걸러짐걸러 줄 화면이 없음 — 도구를 미리 좁혀야 함
출력을 사람이 읽고 판단스크립트가 파싱해야 함 — 형식을 지정해야 함

읽기 전용으로 못 박는 방법은 초급 02에서 배운 --permission-mode plan입니다. 무인 실행에서도 같은 플래그를 씁니다. 정확히는 소스 편집을 막는 것입니다 — plan 모드에서도 Claude는 탐색을 위해 셸 명령을 실행할 수 있고, 파일 편집만 승인 없이는 못 합니다. (출처: code.claude.com/docs/en/permission-modes, 2026-08-26 확인)

4-6. 조직 배포에서 실패하는 방식

여기부터는 실습하지 않고 판단만 다룹니다(3-3). 조직 관리 설정으로 배포된 훅은 사용자·프로젝트·로컬 설정에서 disableAllHooks로 끌 수 없습니다. 관리 설정 수준에서만 끌 수 있습니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

끌 수 없다는 것은 양날입니다

보안 정책으로는 좋습니다. 그러나 잘못 만든 규칙을 배포하면 조직 전체가 막히고, 설정으로는 각자 끌 수 없습니다. 배포 전 검증이 개인 설정보다 훨씬 중요한 이유입니다.

"끌 수 없다"와 "우회할 수 없다"는 다른 말입니다

훅의 matcher는 도구 이름을 정확히 비교합니다. Edit|Write로 등록한 PostToolUse 훅은 Bash로 같은 파일을 고쳐도 실행되지 않습니다 — Bash는 Edit도 Write도 아닌 별개의 도구이기 때문입니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인)

이 모듈을 검수하면서 직접 확인했습니다. 같은 디렉터리에 matcher: "Edit|Write" 훅을 걸어 두고, 한쪽은 Write 도구로, 다른 한쪽은 Bash의 echo로 같은 파일을 고치게 했습니다. Write 쪽은 훅이 실행됐고, Bash 쪽은 파일은 똑같이 바뀌었는데도 훅이 한 번도 실행되지 않았습니다. (CLI 실행 결과 직접 확인, Claude Code v2.1.246, 2026-08-26)

disableAllHooks로 훅 자체를 끄는 것은 관리 설정 수준에서만 가능합니다. 하지만 훅을 끄지 않고도, 그 훅이 보지 않는 도구로 같은 결과를 만들면 훅을 피해 갈 수 있습니다. 공식 문서도 훅의 필터를 하드 차단의 근거로 쓰지 말라고 안내합니다 — 반드시 막아야 하는 동작은 훅이 아니라 권한 시스템(permissions.deny 등)으로 강제하라는 것입니다. (출처: code.claude.com/docs/en/hooks, 2026-08-26 확인) 조직 표준 훅을 설계할 때 Edit|Write만 막고 Bash를 matcher에 넣지 않으면, 배포 자체는 못 꺼도 그 훅이 지키려던 규칙은 도구를 바꿔서 피해 갈 수 있다는 뜻입니다.

배포 실패 유형겉으로 나타나는 모습
내 환경에만 있는 도구에 의존내 기기에서는 완벽. 남의 기기에서 게이트가 조용히 꺼짐(상급 01의 jq 사례)
규칙이 너무 넓음정당한 작업이 막혀 팀이 통째로 우회할 방법을 찾음
버전 요건을 안 밝힘구버전 사용자에게 매처가 다르게 해석됨(상급 01의 4-4)
갱신 책임자가 없음낡은 규칙이 조직 전체에 강제됨(상급 04의 4-6)
되돌리는 방법을 안 정함사고 시 끌 수 있는 사람이 자리에 없음

5. 단계별 실습

실습

만들 결과물: 검증된 CI 게이트 스크립트 1개와, 조직 배포 계획서·위험 평가를 담은 docs/ROLLOUT-PLAN.md.

  1. 무인 실행을 처음 돌려 봅니다

    대화형 세션을 열지 않고 한 번에 실행합니다. 읽기 전용으로 못 박고 시작합니다.

    셸 명령
    cd ~/claude-code-sandbox
claude -p "이 프로젝트의 진입점을 한 줄로 알려 주세요. 파일은 수정하지 마세요." \
  --permission-mode plan

    대화형 화면 없이 결과만 출력되고 종료됩니다.

  2. 종료 코드를 확인합니다
    셸 명령 · 예상 출력
    $ echo $?
0

    이제 일부러 틀린 플래그를 줘 봅니다. 4-2에서 본 대로 실행 전에 stderr로 오류가 나와야 합니다.

    셸 명령
    claude -p "테스트" --nonexistent-flag
echo $?
  3. --bare의 효과를 확인합니다

    4-3의 핵심입니다. 같은 질문을 두 번 던지고 답을 비교합니다.

    셸 명령
    claude -p "이 프로젝트에서 절대 수정하면 안 되는 파일은 무엇인가요?" \
  --permission-mode plan

claude -p "이 프로젝트에서 절대 수정하면 안 되는 파일은 무엇인가요?" \
  --permission-mode plan --bare

    --bare 쪽은 CLAUDE.md를 읽지 않으므로 utils/formatter.py 보호 규칙을 모르거나 근거를 대지 못합니다. 상급 03에서 내장 Explore와 recon을 비교했던 것과 같은 구조입니다.

    여기까지 — 무인 실행의 성질
    • 대화형 화면 없이 실행되고 종료 코드로 분기할 수 있다
    • 잘못된 플래그는 실행 전에 stderr로 보고된다
    • --bare를 붙이면 프로젝트 규칙을 모른다는 것을 직접 확인했다

    두 답이 같다면 CLAUDE.md에 그 규칙이 없거나, 질문이 코드만으로 답할 수 있는 것이었을 수 있습니다. 초급 04의 CLAUDE.md 내용을 확인하세요.

  4. 무엇을 CI에 넣을지 판단합니다

    4-4의 표를 지금 가진 것에 적용합니다. 표를 채우기 전에는 스크립트를 쓰지 마세요.

    가진 것결정론적인가CI에서의 역할
    상급 04 점검 스크립트예빌드 중단
    상급 02 특성화 테스트예빌드 중단
    중급 04 리뷰 스킬아니오조언만
    상급 03 정찰 에이전트아니오조언만

    중단시키는 두 가지에는 Claude가 필요 없습니다. 그래서 --bare 논쟁 자체를 피할 수 있습니다.

  5. CI 게이트 스크립트를 만듭니다

    6번 절의 스크립트 전문을 ci_gate.sh에 저장하고 실행 권한을 줍니다.

    셸 명령
    chmod +x ci_gate.sh
  6. 다섯 가지 상황으로 검증합니다

    상급 01~04에서 반복한 검증 원칙입니다. 게이트는 통과와 차단을 모두 시험해야 합니다.

    상황기대 종료 코드
    A. 정상0
    B. 훅 스크립트 하나 제거1
    C. 특성화 테스트 실패1
    D. 테스트 파일이 하나도 없음1
    E. 원복0
    D를 빼먹기 쉽습니다

    테스트 파일이 없으면 안전망이 비어 있는데도 통과해 버립니다. 이 교재를 만들면서 실제로 이 결함을 발견해 고쳤습니다. 게이트를 만들 때는 "검사할 것이 없는 경우"를 반드시 시험하세요.

    여기까지 — CI 게이트
    • 다섯 상황의 종료 코드가 모두 기대대로다
    • 중단시키는 검사에 Claude가 하나도 안 쓰인다
    • 실패 메시지가 무엇을 해야 하는지 말해 준다

    C가 잡히지 않으면 파이썬 바이트코드 캐시일 수 있습니다. find . -name __pycache__ -type d -exec rm -rf {} + 후 다시 시도하세요.

  7. 비결정론적 조언을 붙입니다 (프롬프트 A)

    게이트를 통과한 뒤 사람이 읽을 조언을 만듭니다. 프롬프트 A를 무인 실행으로 돌립니다.

    이 결과로는 빌드를 막지 않습니다. 4-4의 원칙입니다.

  8. 무인 실행용 프롬프트를 점검합니다

    7단계의 프롬프트가 4-5의 네 가지 함정을 피했는지 확인합니다.

    • 되물을 여지를 남기지 않았는가
    • 필요한 맥락을 프롬프트에 다 넣었는가
    • 읽기 전용으로 못 박았는가
    • 출력 형식을 지정했는가
  9. 배포 계획서를 만듭니다 (프롬프트 B)

    3-3에서 밝힌 대로 실제 배포 대신 계획서를 만듭니다. 프롬프트 B로 초안을 받아 docs/ROLLOUT-PLAN.md로 저장합니다.

  10. 위험 평가를 덧붙입니다 (프롬프트 C)

    4-6의 다섯 가지 실패 유형을 우리 상황에 적용합니다. 프롬프트 C의 결과를 계획서에 이어 붙입니다.

    되돌리는 방법을 반드시 포함하세요. 조직 관리 설정의 훅은 개인이 끌 수 없으므로(4-6), 사고 시 누가 어떻게 끄는지가 계획서의 필수 항목입니다.

    여기까지 — 배포 판단
    • 계획서에 단계별 확산 범위가 있다
    • 다섯 가지 실패 유형이 우리 상황에 맞게 평가됐다
    • 되돌리는 방법과 담당자가 적혀 있다

    되돌리는 방법이 비어 있으면 계획서가 아닙니다. 배포하지 마세요.

6. 예제 코드·예제 프롬프트

실습 자료

예제 코드 — CI 게이트 스크립트 전문

사전 준비물: 상급 04의 .claude/hooks/preflight.py, 상급 02의 tests/. Claude Code는 필요 없습니다.

ci_gate.sh — 발췌가 아닌 전문입니다
#!/bin/sh
# CI 게이트: 컨텍스트 레이어가 살아 있는지 확인한다. Claude를 부르지 않는다.
# 결정론적 검사만 여기 둔다. 판단이 필요한 것은 조언 단계로 분리한다.
cd "$(dirname "$0")" || exit 1
STATUS=0

echo "== 1) 컨텍스트 레이어 점검 =="
if CLAUDE_PROJECT_DIR="$PWD" python3 .claude/hooks/preflight.py; then
  echo "레이어 정상"
else
  echo "레이어 손상 — 고치기 전에는 이 레이어가 지켜 준다고 가정할 수 없습니다" >&2
  STATUS=1
fi

echo
echo "== 2) 특성화 테스트 =="
if [ ! -d tests ]; then
  echo "tests 디렉터리 없음 — 건너뜀"
elif ! ls tests/test_*.py >/dev/null 2>&1; then
  echo "테스트 파일 없음 — 안전망이 비어 있습니다" >&2
  STATUS=1
else
  if python3 -m unittest discover -s tests -q; then
    echo "동작 변화 없음"
  else
    echo "동작이 박제된 결과와 달라졌습니다" >&2
    STATUS=1
  fi
fi

echo
if [ "$STATUS" -eq 0 ]; then echo "게이트 통과"; else echo "게이트 실패" >&2; fi
exit "$STATUS"

설계 판단을 이렇게 했습니다:

선택이유
Claude를 부르지 않음중단시키는 검사는 결정론적이어야 합니다(4-4). 덤으로 --bare 논쟁도 사라집니다
set -e를 쓰지 않음첫 실패에서 멈추면 나머지 검사 결과를 못 봅니다. 모두 실행하고 마지막에 종합합니다
테스트 파일 존재를 따로 확인unittest discover는 테스트가 0개면 조용히 성공(exit 0, "OK")으로 끝납니다 — 직접 실행해 확인했습니다. 이 확인이 없으면 안전망이 통째로 비어 있어도 게이트가 통과해 버립니다. "안전망이 비어 있음"과 "테스트 통과"는 다른 문제입니다
실패 메시지를 stderr로CI 로그에서 성공 출력과 섞이지 않습니다
tests 디렉터리가 없으면 통과특성화 테스트를 안 쓰는 프로젝트에서 가짜 실패를 만들지 않습니다

예상 출력: 정상 상태에서 두 절의 검사 결과와 게이트 통과, 종료 코드 0.

성공 확인 방법: 다섯 상황을 모두 시험합니다.

응답은 매번 다릅니다

아래 "예상 출력"은 응답 예시입니다. 무인 실행이라도 응답은 실행마다 달라지므로, 이 결과로 빌드를 막지 않습니다(4-4).

7. 트러블슈팅

설명
증상원인해결
무인 실행이 중간에 멈춘다 프롬프트가 되물을 여지를 남김 "필요하면 알려 주세요" 같은 표현을 빼고 형식으로만 답하라고 못 박습니다(4-5).
결과가 나왔는데 실은 실패였다 실행 중 실패는 결과로서 stdout에 나옴 stdout만 보지 말고 종료 코드를 함께 확인합니다(4-2).
--bare로 돌리니 답이 얕아졌다 CLAUDE.md와 스킬을 안 읽음 정상 동작입니다(4-3). 프로젝트 규칙이 필요한 작업이면 --bare를 빼거나, 필요한 맥락을 프롬프트에 직접 넣으세요.
게이트가 매번 다른 결과를 낸다 중단 조건에 모델 응답이 섞임 결정론적 검사만 중단시킵니다(4-4). Claude 결과는 아티팩트로만 남기세요.
테스트를 고쳤는데 게이트가 여전히 통과/실패한다 파이썬 바이트코드 캐시 find . -name __pycache__ -type d -exec rm -rf {} + 후 다시 실행합니다. 이 교재를 만들면서 실제로 겪은 문제입니다.

7-2. 흔한 잘못된 습관

습관겉으로 나타나는 모습대응
모델 응답으로 빌드를 막는다 똑똑한 게이트처럼 보임. 같은 코드가 날마다 다르게 판정되어 팀이 게이트를 꺼 버림 막을 것은 결정론적으로 표현할 수 있을 때만 막습니다(4-4). 한 번 꺼진 게이트는 다시 켜지지 않습니다.
안전망이 도는 줄 알고 --bare를 쓴다 빠르고 재현성도 좋음. 훅·CLAUDE.md가 하나도 안 돎 어느 쪽을 쓰든 무엇이 빠지는지 알고 쓰세요(4-3). 안전은 게이트 스크립트가 책임집니다.
한 번에 조직 전체에 배포한다 빠르게 표준화됨. 잘못된 규칙 하나가 전원을 막고 아무도 못 끔 단계별로 확산하고 되돌리기 절차를 먼저 정합니다(4-6).
대화형 프롬프트를 그대로 쓴다 로컬에서는 잘 됨. 무인 실행에서 멈추거나 엉뚱하게 끝남 4-5의 네 가지를 점검합니다(8단계).

이번에 바로잡은 것 (1) — 훅의 우회 가능성: 이전 버전의 4-6은 "각자는 우회할 수 없습니다"라고 써서, disableAllHooks로 훅을 끌 수 없다는 사실과 훅의 matcher를 도구를 바꿔 피해 가는 것을 구분하지 않았습니다. Edit|Write matcher를 쓰는 PostToolUse 훅이 Bash로 같은 파일을 고칠 때는 실행되지 않는다는 것을 CLI로 직접 확인해(2026-08-26) 4-6에 반영했습니다. 이 커리큘럼의 다른 상급 모듈에서도 같은 형태의 문제가 발견됐습니다.

이번에 바로잡은 것 (2) — unittest discover의 실제 동작: 6절의 설계 판단 표는 원래 "테스트가 0개여도 오류로 끝난다"고 썼으나, 직접 실행해 보니 unittest discover는 테스트가 0개면 오류가 아니라 조용히 성공(exit 0)으로 끝났습니다. 표와 참고자료를 이 결과에 맞게 고쳤습니다. 스크립트가 ls tests/test_*.py로 파일 존재를 따로 확인하는 실제 동작 자체는 옳았고, 5개 시나리오(A~E)를 모두 재실행해 기대한 종료 코드(0·1·1·1·0)와 일치함을 확인했습니다.

이번에 바로잡은 것 (3) — 플래그 확인 범위: 이전 버전은 --max-turns·--allowedTools·--json-schema를 "2차 자료에만 있어 미확인"으로 적었으나, 공식 headless 문서·CLI 레퍼런스·GitHub Actions 문서에 모두 나오고, 이번에 CLI로 직접 실행해도 정상 동작했습니다(--max-turns는 claude -h 요약 도움말 목록에는 나오지 않지만 실제로는 동작합니다). 이 모듈은 여전히 실습 범위를 좁게 유지하려고 이 플래그들을 쓰지 않을 뿐, 근거가 불확실해서가 아닙니다.

공식 자료 미확인: 없음. 이번 확인에서 이 모듈이 다루는 범위 안의 구체적 주장은 모두 공식 문서 또는 CLI 직접 실행으로 확인했습니다. 관리 설정 파일을 실제로 기기에 배포해 보는 것은 Owner 권한이 필요해 이 모듈의 실습 범위 밖입니다(3-3).
