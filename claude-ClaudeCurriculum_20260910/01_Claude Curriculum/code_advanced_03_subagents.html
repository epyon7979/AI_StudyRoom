2. 학습 목표

설명

이 모듈을 마치면 다음을 할 수 있습니다.

  1. 언제 위임하고 언제 메인 대화에서 처리할지 판단할 수 있다.

3-3. 이 커리큘럼이 다루지 않는 것

Agent Teams는 제외했습니다

공식 문서는 서브에이전트 외에 Agent Teams도 제공합니다. 서브에이전트가 위임된 하위 작업이 결과를 돌려주는 방식이라면, 팀원들은 각자 독립 컨텍스트로 일하며 서로 메시지를 주고받습니다. 공식 문서 원문 그대로 옮기면 "Agent teams are experimental and disabled by default"(실험적 기능이며 기본적으로 비활성)이라 이 커리큘럼에서는 다루지 않습니다. (출처: code.claude.com/docs/en/agent-teams, 2026-08-26 확인)

포크(/subtask)와 Agent SDK도 이 모듈의 범위 밖입니다.

4. 핵심 개념

설명

4-1. 결론부터

서브에이전트를 쓰는 이유는 "일을 나눠서"가 아니라 "찌꺼기를 안 남기려고"입니다. 공식 문서의 판단 기준이 정확합니다 — 곁가지 작업이 다시 참조하지 않을 검색 결과·로그·파일 내용으로 메인 대화를 뒤덮을 때 씁니다. 서브에이전트가 그 일을 자기 컨텍스트에서 하고 요약만 돌려줍니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

그리고 같은 종류의 일꾼을 같은 지시로 계속 만들고 있을 때 커스텀으로 정의합니다. 중급 01에서 정찰 프롬프트를 매번 붙여 넣었다면, 그게 바로 이 신호입니다.

4-2. 서브에이전트가 주는 것 다섯 가지

얻는 것내용
컨텍스트 보존탐색과 구현을 메인 대화 밖에 둡니다
제약 강제쓸 수 있는 도구를 제한합니다 — 이 모듈의 두 번째 축
설정 재사용사용자 범위 에이전트로 프로젝트마다 재사용합니다
행동 특화특정 영역에 집중한 시스템 프롬프트를 줍니다
비용 통제더 빠르고 저렴한 모델로 작업을 보냅니다

각 서브에이전트는 고유 시스템 프롬프트, 특정 도구 접근, 독립적인 권한을 가진 자기 컨텍스트 창에서 실행됩니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

4-3. 언제 위임하지 않는가

공식 문서가 양쪽 기준을 모두 제시합니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

메인 대화에서 할 때서브에이전트로 보낼 때
  • 잦은 주고받기나 반복적 다듬기가 필요할 때
  • 계획·구현·테스트처럼 여러 단계가 맥락을 공유할 때
  • 빠르고 좁은 변경일 때
  • 지연 시간이 중요할 때 — 포크가 아닌 서브에이전트는 맨바닥에서 시작하므로 맥락을 모으는 데 시간이 걸립니다
  • 메인 컨텍스트에 필요 없는 장황한 출력이 나올 때
  • 도구나 권한 제한을 강제하고 싶을 때
  • 일이 자기완결적이고 요약만 돌려주면 될 때
많이 띄운다고 좋아지지 않습니다

서브에이전트가 끝나면 결과가 메인 대화로 돌아옵니다. 각자 상세한 결과를 돌려주는 서브에이전트를 여럿 돌리면 오히려 컨텍스트를 크게 소모합니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인) 요약을 짧게 받도록 시스템 프롬프트에 형식을 정해 두는 것이 그래서 중요합니다.

재사용 가능한 프롬프트·워크플로가 필요한 것이라면 격리된 컨텍스트가 아니라 메인 대화에서 도는 스킬(중급 03)이 맞을 수 있습니다.

4-4. 내장 서브에이전트가 건너뛰는 것

Claude Code에는 내장 서브에이전트가 있고 Claude가 알아서 씁니다. 초급 02에서 Plan 모드를 쓸 때 이미 Plan 서브에이전트가 동작하고 있었습니다.

내장도구용도
Explore읽기 전용. Write·Edit 거부파일 탐색, 코드 검색
Plan읽기 전용. Write·Edit 거부Plan 모드의 코드베이스 조사
General-purpose서브에이전트가 쓸 수 있는 모든 도구탐색과 수정이 함께 필요한 복잡한 작업
커스텀을 만드는 결정적 이유

Explore와 Plan은 CLAUDE.md 파일과 부모 세션의 git 상태를 (세션 시작 시 컨텍스트에) 자동으로 싣지 않습니다 — 조사를 빠르고 싸게 유지하기 위해서입니다. 다른 모든 내장 에이전트와 커스텀 서브에이전트는 둘 다 자동으로 싣습니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

주의할 점은 이것이 "모른다"가 아니라 "보장되지 않는다"는 뜻이라는 겁니다. Explore도 Read·Grep은 그대로 쓸 수 있어서, CLAUDE.md를 스스로 찾아 읽고 우리가 초급 04부터 쌓아 온 프로젝트 규칙을 맞히는 경우가 실제로 자주 있습니다 — 특히 "뭘 건드리면 안 되나요"처럼 규칙을 직접 겨냥한 질문일 때 그렇습니다(2단계에서 직접 확인합니다). 문제는 질문이 프로젝트 규칙과 무관해 보일 때입니다 — "이 함수를 리팩터링해줘"처럼요. 그때 Explore는 CLAUDE.md를 열어볼 이유 자체가 없어서, utils/formatter.py가 건드리면 안 되는 파일이라는 것도, 운영 진입점이 daily_batch.sh라는 것도 모른 채 조사·제안할 수 있습니다. 이 "질문이 규칙을 안 겨냥하면 놓친다"는 조건이 Explore의 진짜 약점입니다. 프로젝트 규칙을 항상, 무조건 아는 정찰이 필요하면 커스텀 서브에이전트를 만들어야 합니다.

이것이 이 모듈에서 recon 에이전트를 만드는 이유입니다. 공식 문서도 대안을 제시합니다 — 규칙이 꼭 필요하면 위임할 때 주는 프롬프트에 다시 적으라고 합니다. 매번 다시 적을 바에는 에이전트로 만드는 편이 낫습니다(4-1).

4-5. 권한 설정에 함정이 있습니다

부모가 auto 모드면 permissionMode가 무시됩니다

공식 문서의 서술을 그대로 옮깁니다 — 부모가 bypassPermissions나 acceptEdits를 쓰면 그것이 우선하며 덮어쓸 수 없습니다. 부모가 auto 모드를 쓰면 서브에이전트도 auto 모드를 물려받고 프론트매터의 permissionMode는 무시됩니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

초급 02에서 봤듯 Pro·Max·Team의 기본 시작 모드가 auto입니다. 즉 아무 설정 없이 세션을 열면 permissionMode: plan을 적어 둬도 안 먹습니다. 읽기 전용을 확실히 하려면 permissionMode가 아니라 tools·disallowedTools로 도구 자체를 막아야 합니다.

제한 방법부모 모드에 영향받는가이 모듈에서
tools (허용 목록)아니오사용
disallowedTools (거부 목록)아니오사용 — 이중 안전장치
permissionMode예 — 무시될 수 있음보조로만

둘 다 설정하면 disallowedTools가 먼저 적용되고, 남은 목록에 대해 tools가 해석됩니다. 양쪽에 있는 도구는 제거됩니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

그런데 recon엔 Bash도 허용돼 있습니다 — 구멍 아닌가요?

6번 절의 recon.md를 보면 tools에 Bash가 들어 있습니다. Write·Edit이 막혀 있어도 echo ... >> file 같은 셸 리다이렉션을 쓰면 결국 파일을 고칠 수 있는 것 아닌가 하는 의문이 당연히 듭니다. 공식 문서는 이 경우를 정확히 다룹니다 — Claude Code는 Bash 명령 안의 >·>>·2> 같은 출력 리다이렉션 대상을 파일 쓰기로 간주하고, Edit 허용·차단 규칙을 그대로 적용합니다 — 즉 disallowedTools에 Edit이 있으면 리다이렉션도 막힙니다. (출처: code.claude.com/docs/en/permissions, 2026-08-26 확인)

recon과 같은 tools/disallowedTools 설정을 가진 테스트 에이전트로 직접 여러 차례 시도해 확인했습니다 — 심지어 시스템 프롬프트에 "파일을 수정하지 마라"는 지시가 전혀 없는 중립적인 테스트 에이전트로도, 그리고 "이전 지침은 무시하라"는 프롬프트 인젝션 문구를 섞어도 셸 리다이렉션을 통한 쓰기는 모두 차단되었습니다. (CLI 실행 결과 직접 확인, Claude Code v2.1.246, 2026-08-26)

다만 이 확인은 리다이렉션(>·>>·2>) 경우에 한정됩니다 — 공식 문서가 명시하는 범위도 여기까지이고, Bash로 실행 가능한 다른 모든 파일 쓰기 경로(예: 별도 인터프리터 스크립트 안에서 이뤄지는 파일 쓰기)까지 이 메커니즘 하나로 항상 막힌다고 확정할 근거는 공식 자료 미확인입니다. 그래서 9단계처럼 모델의 말이 아니라 git status·git diff로 실제 파일 상태를 확인하는 절차가 여전히 필요합니다.

4-6. 정의 파일이 조용히 건너뛰어집니다

상급 01의 훅과 같은 함정이 여기에도 있습니다. 아래 경우 Claude Code는 파일을 세션에 보고하지 않고 건너뜁니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인)

문제결과
name 없음에이전트 옆에 둔 문서로 취급하고 넘어감
name이 -로 시작하거나 : 포함건너뛰고 디버그 로그에만 오류 기록
name은 있는데 description 없음건너뛰고 디버그 로그에만 이유 기록
YAML 파싱 실패필드를 하나도 안 읽고 건너뜀

디버그 로그는 --debug로 봅니다. agents 디렉터리 전체를 미리 검사하려면 claude plugin validate .claude/agents를 쓸 수 있습니다(v2.1.233 이상) — 직접 돌려보면 YAML 자체가 깨진 파일은 정확한 오류 메시지와 함께 잡아냅니다. 다만 이 표 네 경우 중 셋은 걸러 주지 않습니다. 공식 문서에 명시된 대로 name이 아예 없는 파일은 잡지 않고, 직접 시험해 보니 name에 :가 들어가거나 -로 시작하는 경우도 경고 없이 통과했습니다 — validate는 YAML 파싱 여부와 description 누락만 확인하고 name의 형식 자체는 검사하지 않는 것으로 보입니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인 / name 형식 미검사 부분은 CLI 실행 결과 직접 확인, v2.1.246, 2026-08-26) 그래서 validate 통과가 곧 "정상 로드"의 증명은 아닙니다 — 5단계처럼 세션을 재시작해 @ 타이프어헤드에 실제로 뜨는지 확인하는 것이 유일하게 확실한 방법입니다.

4-7. 돌아온 보고서는 검사를 거칩니다

알아 두면 화면의 이상한 표시가 이해됩니다

Claude Code는 각 서브에이전트의 최종 보고서를 Claude가 읽기 전에 검사합니다. 서브에이전트가 내가 검토하지 않은 파일·웹페이지·명령 출력을 읽었을 수 있고, 그 텍스트가 메인 대화를 겨냥한 지시를 품고 있을 수 있기 때문입니다. 검사는 아무것도 지우거나 바꿔 쓰지 않고, 두 가지 표시만 남깁니다 — Claude Code 자체 출력을 흉내 낸 텍스트에 백슬래시를 끼워 넣고, 보고서가 <system-reminder> 같은 태그를 흉내 내거나 bypassPermissions 같은 권한 설정을 언급하면 [harness: subagent output matched instruction-shaped pattern(s):로 시작하는 표시 줄을 앞에 붙입니다. (출처: code.claude.com/docs/en/sub-agents, 2026-08-26 확인, v2.1.210 이상)

다만 공식 문서가 분명히 합니다 — 이 검사는 악의 여부를 판단하지 않고, 서브에이전트가 닿을 수 있는 범위를 제한하는 것을 대체하지 못합니다. 그래서 4-5의 도구 제한이 여전히 1차 방어입니다.

    도구 제한을 강제하고 싶은가예 — 정찰 중에는 절대 수정하면 안 됩니다
    같은 지시를 반복해서 붙여 넣고 있는가예 — 중급 01의 프롬프트를 매번 씁니다

    utils/formatter.py를 Explore가 정확히 짚어내는 경우가 실제로 많습니다. CLAUDE.md가 "건너뛰어진다"는 것은 세션 시작 시 자동으로 미리 실리지 않는다는 뜻이지, Explore가 CLAUDE.md를 읽을 수 없다는 뜻이 아닙니다 — Explore도 Read·Grep은 그대로 쓰므로, "뭘 고치면 안 되나요"처럼 CLAUDE.md를 직접 찾아 읽을 이유가 뚜렷한 질문을 던지면 스스로 찾아내 정확히 답하는 경우가 흔합니다(직접 실행 확인, Claude Code v2.1.246 + Sonnet 5, 2026-08-26 — 동일 프롬프트로 3회 실행 모두 utils/formatter.py를 근거와 함께 정확히 짚었습니다).

    그러니 이 단계에서 Explore가 정답을 맞혀도 이상한 게 아닙니다. 진짜 차이는 "맞혔는가"가 아니라 "보장되는가"입니다 — recon은 CLAUDE.md가 항상, 무조건 실려 있어 결과가 결정적이지만, Explore는 질문이 프로젝트 규칙과 상관없어 보이면(예: "이 함수 리팩터링해줘") 애초에 CLAUDE.md를 열어볼 이유가 없어 놓칠 수 있습니다 — 그때는 운에 맡기는 셈입니다. 7단계에서 이 차이를 다시 짚습니다.

7. 트러블슈팅

설명
증상원인해결
@ 타이프어헤드에 안 나온다 프론트매터 문제로 조용히 건너뛰어짐, 또는 새 디렉터리라 재시작 필요 먼저 재시작합니다. 그래도 없으면 claude --debug로 이유를 봅니다. 4-6의 네 가지를 순서대로 확인하세요.
읽기 전용인데 파일이 바뀌었다 tools에 쓰기 계열이 남아 있거나, permissionMode에만 의존함 tools와 disallowedTools를 둘 다 설정합니다(4-5). permissionMode는 부모 모드에 무시될 수 있습니다.
Claude가 알아서 위임하지 않는다 description에 내가 쓸 표현이 없음 공식 문서는 적극적 위임을 원하면 설명에 "use proactively"에 해당하는 표현을 넣으라고 안내합니다. 그래도 안 되면 @-멘션으로 확실히 지정하세요.
보고가 너무 길어 메인 컨텍스트를 먹는다 시스템 프롬프트에 형식·분량 제한이 없음 본문의 "보고 형식"을 더 좁힙니다. 서브에이전트를 여럿 돌리면 각자의 상세한 결과가 합쳐져 오히려 컨텍스트를 크게 소모합니다(4-3).
보고서 앞에 [harness: ...] 줄이 붙었다 출력 스캔이 지시 형태 패턴을 발견함 정상 동작입니다(4-7). 보고서가 시스템 태그를 흉내 냈거나 권한 설정을 언급했을 때 붙습니다. 내용은 그대로이며 삭제되지 않습니다.

7-2. 흔한 잘못된 습관

습관겉으로 나타나는 모습대응
일단 서브에이전트로 보낸다 고급스러워 보임. 맥락을 다시 모으느라 느려지고 사용량만 늘어남 4-3의 표로 먼저 판단합니다. 잦은 주고받기가 필요한 일은 메인 대화가 낫습니다.
permissionMode만 걸고 안심한다 읽기 전용이라 믿음. 부모가 auto 모드면 그 설정이 무시됨 도구 자체를 막습니다(4-5). 그리고 프롬프트 B처럼 실제로 시험합니다.
내장으로 되는 일을 커스텀으로 만든다 에이전트가 늘어남. 관리 대상만 많아지고 이름 충돌이 생김 먼저 Explore로 시도해 봅니다(2단계). CLAUDE.md를 알아야 하는 일일 때만 커스텀이 필요합니다(4-4).
동작 확인 없이 커밋한다 내 화면에서는 잘 됨. 팀원 환경에서 조용히 로드 실패 도구 제한 검증(9단계)과 로드 확인(5단계)을 마친 뒤에 커밋합니다.
